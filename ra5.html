    Unidad 5 · 1. Herramientas · 2 horas

    Herramientas del despliegue en contenedores

    CE 5a

    Objetivos del punto

    • Enumerar las herramientas que intervienen en cada paso del despliegue de una aplicación en contenedores.
    • Describir el objetivo, las características y el funcionamiento de los motores de contenedores, las herramientas de construcción, los registros, los orquestadores y las herramientas de automatización.
    • Seguir en el portátil el recorrido de una imagen: construirla, ejecutarla y ver qué procesos intervienen.

    1. Del código al contenedor en marcha

    Desplegar en contenedores es recorrer siempre la misma cadena: el código se guarda en un repositorio, se construye una imagen, la imagen se publica en un registro y desde allí se descarga y ejecuta en los servidores. Cada paso tiene sus herramientas, y una herramienta de CI/CD automatiza la cadena completa.

    Lo que hace posible que herramientas de fabricantes distintos encajen entre sí es el estándar de la Open Container Initiative (OCI). Define el formato de las imágenes, cómo se ejecuta un contenedor y cómo se distribuyen las imágenes desde un registro. Por eso una imagen construida con Docker se puede publicar en Harbor y ejecutar con Podman o con Kubernetes.

    2. Motores de contenedores

    El motor es el software que descarga las imágenes y crea los contenedores en el sistema operativo, aislándolos con los namespaces y los cgroups del núcleo de Linux.

    Docker

    Popularizó los contenedores en 2013 y sigue siendo el más usado en desarrollo. Funciona con una arquitectura cliente-servidor:

    docker (CLI) ──API REST──► dockerd (demonio) ──► containerd ──► runc ──► contenedor
                                  │
                                  └── BuildKit (construcción de imágenes)

    La orden docker no crea nada: envía peticiones al demonio dockerd, que se ejecuta como root. Este delega en containerd, que gestiona el ciclo de vida de las imágenes y los contenedores, y containerd usa runc para crear cada contenedor según la especificación OCI. Docker Engine en Linux es libre. Docker Desktop, la versión para Windows y macOS, es de pago para empresas grandes.

    Podman

    Alternativa de Red Hat compatible con las órdenes de Docker (podman run, podman build...). Su diferencia principal es que no tiene demonio: cada contenedor es un proceso hijo de quien lo lanza, y por defecto se ejecuta sin root (rootless). Si alguien escapa de un contenedor, llega a un usuario sin privilegios y no al administrador del equipo. Agrupa contenedores en pods, como Kubernetes.

    containerd y CRI-O

    Motores sin interfaz para personas, pensados para que los use un orquestador. Kubernetes habla con ellos mediante la interfaz CRI. Hoy la mayoría de clústeres de Kubernetes ejecutan los contenedores con containerd o con CRI-O, no con Docker.

    3. Construcción de imágenes

    Una imagen se describe en un Dockerfile: una imagen base y una lista de instrucciones (FROM, COPY, RUN, CMD...). Cada instrucción que modifica ficheros genera una capa. Las capas se reutilizan entre imágenes y entre construcciones, por eso conviene copiar primero lo que cambia poco (las dependencias) y al final lo que cambia mucho (el código).

    • BuildKit: el motor de construcción de Docker. Construye en paralelo las partes independientes y guarda en caché las capas.
    • Buildah: construye imágenes OCI sin demonio. Es el que usa Podman por debajo.
    • Kaniko: construye imágenes dentro de un contenedor sin privilegios. Se usa en pipelines que se ejecutan en Kubernetes, donde no hay un demonio de Docker disponible.

    4. Registros de imágenes

    Un registro almacena, versiona y distribuye imágenes. Cada imagen se identifica con un nombre y una etiqueta (ghcr.io/empresa/api:1.0.0) y, además, con un digest, el hash de su contenido (sha256:...). La etiqueta se puede mover a otra imagen. El digest no cambia nunca, por eso es la forma más segura de fijar una versión.

    • Docker Hub: el registro público por defecto. Limita las descargas de usuarios sin cuenta.
    • GitHub Container Registry (ghcr.io): integrado con los repositorios y los permisos de GitHub. Es el que usaremos.
    • Harbor (CNCF): registro que se instala en servidores propios, con control de acceso por proyectos y escaneo de vulnerabilidades integrado.
    • Registros de los proveedores de nube: Amazon ECR, Azure Container Registry, Google Artifact Registry.

    5. Varios contenedores y orquestación

    Una aplicación real tiene varios contenedores (la API, la base de datos, la caché) y necesita que alguien los mantenga vivos.

    • Docker Compose: describe en un fichero YAML los contenedores de una aplicación, sus redes y sus volúmenes, y los arranca juntos en un solo equipo. Muy usado en desarrollo y en pruebas.
    • Kubernetes: el orquestador estándar para ejecutar contenedores en muchos servidores. Es declarativo: se describe el estado deseado (cuántas réplicas de qué imagen) y sus controladores trabajan en bucle para mantenerlo, reiniciando contenedores caídos, repartiendo la carga y actualizando sin cortes. Helm empaqueta aplicaciones para Kubernetes. Lo veréis a fondo en el módulo 5166.
    • Docker Swarm y Nomad: orquestadores más sencillos y menos extendidos.
    • Servicios gestionados: Amazon EKS, Azure AKS o Google GKE ofrecen Kubernetes gestionado, y Amazon ECS, Azure Container Apps o Google Cloud Run ejecutan contenedores sin gestionar servidores (unidad 4).

    6. Automatizar el despliegue

    • CI/CD: GitHub Actions y GitLab CI definen los pasos en ficheros YAML dentro del propio repositorio y los ejecutan en máquinas temporales (runners) cuando ocurre un evento, como un push. Jenkins es un servidor propio, muy flexible gracias a sus plugins, pero hay que instalarlo y mantenerlo. Desde el punto 5 usaremos GitHub Actions.
    • GitOps: Argo CD y Flux se ejecutan dentro de Kubernetes y comparan continuamente lo que hay desplegado con lo declarado en un repositorio Git. Para desplegar, basta con fusionar un cambio en Git.
    • Infraestructura y configuración: Terraform crea la infraestructura donde se ejecutan los contenedores (unidad 6) y Ansible instala y configura el software de los servidores (unidad 7).

    Unidad 5 · 2. Calidad y seguridad · 2 horas

    Herramientas de validación de calidad y seguridad del código

    CE 5b

    Objetivos del punto

    • Clasificar las herramientas que validan la calidad y la seguridad del código, de las dependencias y de las imágenes.
    • Describir las características y aplicaciones de cada tipo: linters, pruebas, análisis estático, SAST, SCA, detección de secretos, escaneo de imágenes y de configuración, y DAST.
    • Interpretar los resultados de estas herramientas y decidir en qué momento del pipeline se ejecuta cada una.

    1. Por qué validar antes de desplegar

    Cada cambio que llega a producción puede introducir errores, código difícil de mantener, vulnerabilidades o dependencias con fallos conocidos. Revisarlo todo a mano es imposible cuando se despliega a menudo. La solución DevOps es automatizar las comprobaciones y ejecutarlas en cada cambio, lo antes posible. Es el principio de desplazar a la izquierda (shift left): en un diagrama del ciclo de vida dibujado de izquierda a derecha, las comprobaciones se mueven hacia el principio, donde corregir es más barato. Integrar así la seguridad en todo el ciclo es lo que se llama DevSecOps.

    2. Herramientas de calidad del código

    Formateadores y linters

    • Formateadores: reescriben el código con un estilo uniforme (ruff format o Black en Python, Prettier en JavaScript). Evitan discusiones de estilo en las revisiones.
    • Linters: analizan el código sin ejecutarlo en busca de errores probables y malas prácticas: variables sin usar, importaciones que faltan, comparaciones sospechosas, complejidad excesiva. Ejemplos: Ruff y Pylint (Python), ESLint (JavaScript), hadolint (Dockerfile), ShellCheck (Bash), yamllint, ansible-lint y terraform validate.

    Pruebas automáticas

    TipoQué pruebaVelocidadHerramientas
    UnitariasUna función o clase aisladaMilisegundospytest, JUnit, Jest
    De integraciónVarios componentes juntos (aplicación y base de datos, o el contenedor real)Segundospytest con contenedores, Docker Compose
    Extremo a extremo (E2E)El sistema completo como lo usaría una personaMinutosPlaywright, Selenium, Cypress
    De rendimiento y cargaComportamiento con muchos usuariosMinutosk6, JMeter, Locust

    La pirámide de pruebas recomienda muchas pruebas unitarias, bastantes de integración y pocas E2E, porque estas son lentas y frágiles. La cobertura mide qué porcentaje del código se ejecuta durante las pruebas (pytest-cov en Python, JaCoCo en Java). Una cobertura alta no garantiza buenas pruebas, pero una baja indica que hay código sin probar.

    Análisis estático de calidad

    SonarQube (instalado en servidores propios) y SonarQube Cloud (SaaS, gratuito para proyectos públicos) analizan el código en decenas de lenguajes y clasifican los problemas en fiabilidad (bugs), mantenibilidad (código duplicado, complejidad, deuda técnica) y seguridad. Su concepto central es el quality gate: un conjunto de condiciones que debe cumplir el código nuevo para aprobar (por ejemplo, cobertura de al menos un 80 % y ninguna vulnerabilidad nueva). Si no se cumple, el pipeline falla y el cambio no se puede fusionar. Aplicarlo solo al código nuevo evita que la deuda crezca sin obligar a arreglar todo lo antiguo de golpe.

    Revisión de código

    La revisión por otra persona en el pull request sigue siendo imprescindible: detecta problemas de diseño y de lógica que ninguna herramienta ve. Las herramientas automáticas liberan a quien revisa de lo mecánico.

    Conceptos que hay que conocer

    • CVE (Common Vulnerabilities and Exposures): identificador público de una vulnerabilidad conocida, como CVE-2021-44228 (Log4Shell). Las herramientas SCA y de imágenes buscan CVE en las versiones que usamos. GitHub publica además sus propios avisos con identificadores GHSA-....
    • CVSS: puntuación de gravedad de 0 a 10 (baja, media, alta, crítica). Ayuda a priorizar, aunque hay que valorar si la parte vulnerable se usa realmente.
    • Bases de datos de vulnerabilidades: NVD (EE. UU.), GitHub Advisory Database, OSV.
    • Falsos positivos: avisos que no son un problema real. Se revisan y se descartan con una justificación. Ignorarlos sin más hace que se pierda la confianza en la herramienta.

    Unidad 5 · 3. Mínimo privilegio · 2 horas

    Usuarios, perfiles y entornos: el principio de mínimo privilegio

    CE 5c

    Objetivos del punto

    • Aplicar el principio de mínimo privilegio, el control de acceso basado en roles y la separación de funciones.
    • Definir perfiles con equipos y roles en una organización de GitHub.
    • Habilitar el acceso a los recursos de despliegue: entornos de revisión y producción con reglas y secretos propios, permisos de los workflows y del registro de imágenes.
    • Comprobar que los perfiles permiten lo que deben y limitan lo que no.

    1. Principios de control de acceso

    • Autenticación: comprobar quién eres (contraseña, doble factor, clave SSH, token). Autorización: decidir qué puedes hacer. Auditoría: registrar qué has hecho, para poder revisarlo.
    • Mínimo privilegio: cada persona y cada proceso tiene solo los permisos que necesita, solo sobre los recursos que necesita y solo durante el tiempo que los necesita. Si una cuenta se ve comprometida, el daño queda limitado a lo que esa cuenta podía hacer.
    • Control de acceso basado en roles (RBAC): no se dan permisos persona a persona. Se definen roles (conjuntos de permisos) y grupos (conjuntos de personas), y se asigna un rol a un grupo sobre un recurso. Cuando alguien entra, cambia de puesto o se va, solo hay que moverlo de grupo.
    • Separación de funciones: una acción crítica no la puede completar una sola persona. Quien escribe un cambio no puede aprobarlo y desplegarlo en producción sin que otra persona lo revise.
    • Identidades de máquina: los procesos (el pipeline, Terraform, Ansible) también acceden a recursos. Tienen sus propias credenciales con permisos mínimos, nunca las de una persona del equipo.

    2. Perfiles en GitHub

    Organización

    Una organización agrupa los repositorios y las personas de un proyecto o empresa. Sus roles son Owner (control total, incluida la seguridad y la facturación) y Member, que participa según los permisos de sus equipos. En la configuración se fijan los permisos base de los miembros sobre todos los repositorios (recomendado: ninguno o lectura), si pueden crear repositorios y si se les exige doble factor. En una empresa debe haber al menos dos owners, y muy pocos.

    Equipos y roles de repositorio

    Los equipos agrupan miembros. A cada equipo se le da un rol sobre cada repositorio:

    RolPuedePensado para
    ReadVer y clonar el código, abrir issues y comentarAuditoría, personas interesadas
    TriageAdemás, gestionar issues y pull requestsGestión del proyecto
    WriteAdemás, crear ramas, hacer push y fusionar pull requests si las reglas lo permitenDesarrollo
    MaintainAdemás, gestionar parte de la configuración del repositorio sin acceso a lo sensibleResponsables del proyecto
    AdminTodo: configuración, reglas, secretos, borrar el repositorioMuy pocas personas

    3. Acceso a los recursos de despliegue

    El criterio no pide solo dar acceso al código, sino a los recursos y herramientas con los que se despliegan y gestionan los entornos. En GitHub son tres: los entornos, el token de los workflows y el registro de imágenes.

    Entornos

    Un entorno (environment) representa un destino de despliegue, como revision o produccion. Cada uno tiene:

    • Secretos y variables propios: la contraseña de la base de datos de producción solo la recibe un trabajo que despliega en producción.
    • Reglas de protección: revisores obligatorios (el trabajo queda en pausa hasta que una persona o equipo autorizado lo aprueba), ramas permitidas (a producción solo se despliega desde main) e impedir que quien lanza el despliegue se lo apruebe a sí mismo.
    • Historial de despliegues: qué versión hay en cada entorno y quién la aprobó.

    Un trabajo de un workflow entra en un entorno con la clave environment. Desde ese momento se le aplican sus reglas y recibe sus secretos.

    El token de los workflows

    Cada ejecución de GitHub Actions recibe un token temporal, GITHUB_TOKEN, que caduca al terminar el trabajo. Por mínimo privilegio se configura como solo lectura por defecto, y cada workflow pide de forma explícita lo que necesita con la clave permissions. Por ejemplo, solo el trabajo que publica la imagen pedirá packages: write (punto 7).

    El registro de imágenes

    Las imágenes que un workflow publica en ghcr.io quedan vinculadas al repositorio y heredan sus permisos: quien puede leer el repositorio puede descargar la imagen y solo el workflow con packages: write puede publicarla. Los servidores que descargan la imagen usan un token propio de solo lectura (read:packages), distinto en cada entorno. Lo configuraremos en la unidad 6.

    1. Autenticación: quién accede

    Personas

    • Contraseña y doble factor (2FA): con una aplicación de autenticación (TOTP), una llave de seguridad física o una passkey. GitHub exige 2FA a quien contribuye código, y una organización puede exigirlo a todos sus miembros. Los códigos de recuperación se guardan en un lugar seguro.
    • Claves SSH para trabajar con Git desde el portátil. Se genera un par de claves: la privada no sale nunca del portátil y se protege con una frase de paso, y la pública se registra en GitHub. Se recomienda el tipo ed25519 y una clave por persona y por dispositivo, para poder revocar solo la del portátil perdido.
    • Git por HTTPS no admite contraseñas: necesita un token o el gestor de credenciales.

    2. Autorización: qué se puede hacer con el código

    Los equipos y sus roles (punto 3) dicen quién puede escribir. Las reglas de protección dicen cómo tiene que hacerlo.

    Reglas de protección (rulesets)

    Un ruleset aplica políticas a las ramas o etiquetas que coinciden con un patrón. Se aplica a todo el mundo, owners incluidos, salvo a quien se añada a su lista de excepciones (bypass list). Las reglas más importantes para la rama main:

    ReglaQué impide o exige
    Restringir borradosQue alguien borre la rama
    Bloquear force pushReescribir el historial ya publicado
    Exigir pull requestHacer push directo: todo cambio pasa por un pull request
    Aprobaciones requeridasFusionar sin un número mínimo de revisiones aprobadas
    Descartar aprobaciones con nuevos commitsAprobar una versión y colar otra después
    Revisión de los propietarios del códigoFusionar cambios en ciertas rutas sin la aprobación de su responsable
    Resolver conversacionesFusionar con comentarios de revisión pendientes
    Comprobaciones de estado obligatoriasFusionar si las pruebas y los análisis no están en verde (punto 5)

    También se protegen las etiquetas de versión (v*), para que nadie mueva ni borre la etiqueta de una versión ya publicada.

    CODEOWNERS

    El fichero .github/CODEOWNERS asigna equipos responsables a rutas del repositorio. Cuando un pull request toca esas rutas, se pide automáticamente su revisión y, con la regla correspondiente, es obligatoria. Si varias líneas coinciden con un fichero, manda la última:

    .github/CODEOWNERS

    *               @ORGANIZACION/desarrollo
Dockerfile      @ORGANIZACION/operaciones
/.github/       @ORGANIZACION/operaciones

    Así, un cambio en los workflows o en la forma de construir la imagen siempre lo aprueba operaciones, y un cambio en el código de la aplicación lo aprueba desarrollo. Como nadie puede aprobar su propio pull request, en vuestra pareja los cambios de .github/ los propondrá la persona de desarrollo y los aprobará la de operaciones: es la separación de funciones del punto 3.

    3. Otros parámetros de seguridad del repositorio

    • Visibilidad: público, privado o interno. Un repositorio público nunca debe contener secretos ni datos personales.
    • Detección de secretos y alertas de dependencias: las activaremos en el punto 6.
    • Commits firmados: Git deja poner cualquier nombre en un commit. Firmándolos con una clave SSH o GPG, GitHub muestra la marca Verified y garantiza la autoría. Un ruleset puede exigirlos.
    • Registro de auditoría de la organización: quién cambió permisos, reglas o secretos y cuándo.
    • Revisión periódica de miembros, claves de despliegue y tokens autorizados.

    Idea clave. La seguridad del acceso al código combina tres capas: quién entra (autenticación fuerte y credenciales de máquina limitadas), qué puede hacer (equipos y roles) y cómo debe hacerlo (reglas que obligan a revisar y validar cada cambio).

    1. GitHub Actions

    Un workflow es un fichero YAML en la carpeta .github/workflows/ del repositorio. Sus piezas:

    ElementoQué esEjemplo

    3. El workflow de calidad

    .github/workflows/calidad.yml

    name: Calidad
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  pruebas:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
          cache: pip
      - name: Instalar dependencias
        run: pip install -r requirements-dev.txt
      - name: Linter
        run: ruff check . --output-format=github
      - name: Formato
        run: ruff format --check .
      - name: Pruebas y cobertura
        run: pytest --cov=. --cov-report=term-missing --cov-fail-under=80

    El ejemplo clásico de lo primero es Log4Shell (CVE-2021-44228, diciembre de 2021): una vulnerabilidad crítica en Log4j, una librería de registros de Java presente en miles de aplicaciones que llevaban años sin cambiar. Las organizaciones que comprobaban su código de forma periódica supieron en horas qué sistemas estaban afectados. Las demás tardaron semanas.

    2. CodeQL: el código propio

    CodeQL es el motor SAST de GitHub, gratuito para repositorios públicos. Funciona en dos fases:

    1. Extracción: convierte el código en una base de datos que representa su estructura, el flujo de los datos y el flujo de control.
    2. Consultas: ejecuta consultas que buscan patrones de vulnerabilidad. La más importante es el análisis de flujo de datos contaminados (taint tracking): sigue un dato que entra desde el usuario (la fuente, por ejemplo un parámetro de la petición) hasta un punto peligroso (el sumidero, por ejemplo una consulta SQL) sin pasar por ninguna validación.

    Se activa con la configuración por defecto, con un clic y sin escribir ningún fichero. A partir de ese momento analiza cada push y cada pull request a main y, además, una vez por semana, aunque nadie haya cambiado el código. Los resultados aparecen en la pestaña Security → Code scanning y como comentarios en la línea afectada de los pull requests.

    3. Detección de secretos

    • Secret scanning: busca en todo el historial del repositorio credenciales de cientos de proveedores (AWS, Azure, Google, Slack, tokens de GitHub...). Se ejecuta de forma continua y, en repositorios públicos, avisa también al proveedor para que revoque la credencial.
    • Push protection: rechaza el push que contiene una credencial antes de que llegue al repositorio. Prevenir es mejor que detectar: un secreto publicado sigue en el historial aunque se borre en el siguiente commit.

    Si se filtra un secreto: primero se revoca o se cambia en el servicio, después se revisan los registros para ver si alguien lo ha usado y, por último, si se quiere, se limpia del historial. Borrarlo del código no sirve de nada si no se revoca.

    4. OpenSSF Scorecard: la configuración de seguridad

    Scorecard es una herramienta libre de la OpenSSF (Open Source Security Foundation, de la Linux Foundation). Lee la configuración del repositorio y sus ficheros, ejecuta una serie de comprobaciones y da a cada una una nota del 0 al 10. Las que no llegan al 10 aparecen como alertas en Security → Code scanning, con su nota y el motivo. Estas son las que tienen que ver con lo que habéis configurado:

    ComprobaciónQué verificaDónde lo configurasteis

    Code-ReviewQue los últimos cambios de main los ha revisado otra personaPull requests aprobados (puntos 4 y 5)

│ ┌─────── hora (0-23)
│ │ ┌───── día del mes (1-31)
│ │ │ ┌─── mes (1-12)

    Unidad 5 · 7. Dependencias · 2 horas

    Validar dependencias e integración antes de desplegar

    CE 5g

    Objetivos del punto

    • Identificar los riesgos de las dependencias externas y de la cadena de suministro del software.
    • Fijar las versiones de las dependencias para que lo validado sea lo que se despliega.
    • Validar las dependencias nuevas en cada pull request.
    • Construir la imagen, escanearla y probar su integración antes de publicarla.

    1. El problema de las dependencias

    Una aplicación tiene muy poco código propio: la mayor parte son dependencias. cita-previa-app declara dos (Flask y Gunicorn), pero al instalarlas se descargan también sus dependencias transitivas, y la imagen de contenedor añade cientos de paquetes del sistema operativo. Todo ese código de terceros se ejecuta con los permisos de nuestra aplicación.

    Riesgos

    • Vulnerabilidades conocidas en versiones concretas.
    • Paquetes maliciosos: publicados con nombres parecidos a otros populares (typosquatting, como reqeusts en lugar de requests) o legítimos cuya cuenta de publicación ha sido robada.
    • Ataques a la cadena de suministro: introducir código malicioso en un proyecto de confianza. Casos reales: la puerta trasera de xz-utils (2024), preparada durante años y descubierta por casualidad poco antes de llegar a las distribuciones Linux, y el ataque a Trivy de marzo de 2026, que se explica en el apartado 4.
    • Proyectos abandonados que ya no reciben correcciones.
    • Cambios incompatibles al actualizar, que rompen la aplicación.
    • Licencias incompatibles con el uso que se quiere hacer del software.

    2. Fijar y actualizar las dependencias

    El versionado semántico (MAYOR.MENOR.PARCHE) indica el tipo de cambio: el parche corrige errores, la menor añade novedades compatibles y la mayor rompe la compatibilidad. Si se declaran rangos (flask>=3), dos construcciones hechas en días distintos pueden instalar versiones diferentes. Por eso, en lo que se despliega, las versiones se fijan: flask==3.1.3 en requirements.txt y python:3.12-slim en el Dockerfile. Para fijar también las transitivas se usan ficheros de bloqueo (poetry.lock, uv.lock, package-lock.json).

    Fijar no significa no actualizar nunca, sino actualizar de forma deliberada y validada. Dependabot, que configurasteis en el punto 6, abre pull requests con las actualizaciones, y cada una pasa por las comprobaciones de este punto antes de fusionarse.

    3. Validar las dependencias en cada pull request

    La acción dependency-review compara las dependencias del pull request con las de main y falla si el cambio introduce una versión con vulnerabilidades conocidas. También informa de las licencias. pip-audit revisa además todas las dependencias de Python contra la base de datos de PyPI. Se añade como un segundo trabajo al workflow de calidad:

    .github/workflows/calidad.yml (trabajo nuevo)

      dependencias:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/dependency-review-action@v4
        with:
          fail-on-severity: moderate
      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
      - name: pip-audit
        run: pip install pip-audit && pip-audit -r requirements.txt

    4. Validar la integración antes de publicar

    Que cada pieza pase sus pruebas no garantiza que funcionen juntas. Las pruebas unitarias del punto 5 prueban el código con Flask, pero no la imagen tal como se desplegará: con Gunicorn, su usuario, su puerto y su configuración. Las pruebas de integración se hacen contra el contenedor real:

    1. Construir la imagen una sola vez.
    2. Escanearla con Trivy: si tiene vulnerabilidades críticas con corrección disponible, se para.
    3. Arrancarla con la configuración de un entorno y esperar a que su healthcheck diga que está sana.
    4. Probar el contenedor en marcha: responde en /salud con el entorno correcto, devuelve citas, devuelve 404 donde debe y no se ejecuta como root.
    5. Solo si todo pasa, publicar la imagen en el registro, y solo desde main o desde una etiqueta de versión.

    Las integraciones externas (un proveedor de SMS, una pasarela de pago) no se prueban contra el servicio real de producción. Se usan los entornos de pruebas (sandbox) del proveedor o simulaciones con el mismo contrato, y pruebas de contrato que avisan si el proveedor cambia el formato de sus respuestas.

    .github/workflows/imagen.yml

    name: Imagen
on:
  pull_request:
  push:
    branches: [main]
    tags: ["v*"]
permissions:
  contents: read                   # todo el workflow, solo lectura
jobs:
  construir-probar-publicar:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write              # solo este trabajo puede publicar imágenes
    steps:
      - uses: actions/checkout@v5
      - name: Construir
        run: docker build -t app:ci .
      - name: Escanear la imagen
        uses: aquasecurity/trivy-action@v0.35.0
        with:
          image-ref: app:ci
          severity: CRITICAL
          ignore-unfixed: true
          exit-code: "1"
      - name: Arrancar el contenedor
        run: |
          docker run -d --name app -p 8000:8000 -e ENTORNO=ci app:ci
          for i in $(seq 1 30); do
            if [ "$(docker inspect -f '{{.State.Health.Status}}' app)" = healthy ]; then exit 0; fi
            sleep 2
          done
          docker logs app
          exit 1
      - name: Pruebas de integración
        run: |
          curl -fsS localhost:8000/salud | jq -e '.entorno == "ci"'
          curl -fsS localhost:8000/citas | jq -e 'length >= 1'
          test "$(curl -s -o /dev/null -w '%{http_code}' localhost:8000/no-existe)" = 404
          test "$(docker exec app whoami)" != root
      - name: Publicar (solo desde main o desde una etiqueta)
        if: github.event_name == 'push'
        run: |
          echo "${{ secrets.GITHUB_TOKEN }}" | docker login ghcr.io -u "${{ github.actor }}" --password-stdin
          IMAGEN=$(echo "ghcr.io/${{ github.repository }}" | tr '[:upper:]' '[:lower:]')
          docker tag app:ci "$IMAGEN:sha-${GITHUB_SHA::7}"
          docker push "$IMAGEN:sha-${GITHUB_SHA::7}"
          if [[ "$GITHUB_REF" == refs/tags/v* ]]; then
            docker tag app:ci "$IMAGEN:${GITHUB_REF_NAME#v}"
            docker push "$IMAGEN:${GITHUB_REF_NAME#v}"
          fi

    La acción de Trivy que usa este workflow es un buen ejemplo de ataque a la cadena de suministro. En marzo de 2026, unos atacantes con credenciales robadas movieron casi todas las etiquetas de versión de aquasecurity/trivy-action a un código que robaba los secretos de los pipelines que la usaban. Tras el incidente se borraron las etiquetas antiguas y la primera segura es la v0.35.0. Por eso Scorecard pide fijar las acciones por el hash de su commit, que no se puede mover (punto 6).

    Cada imagen publicada desde main lleva como etiqueta el hash corto del commit (sha-1a2b3c4), y la publicada desde una etiqueta v1.0.0 se etiqueta además como 1.0.0. Es la imagen que desplegarán las unidades 6 y 7.
