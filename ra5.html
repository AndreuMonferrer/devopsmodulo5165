    2. Cómo clasificar una herramienta

    Más allá de la etapa, conviene analizar cómo funciona:

    • Declarativa o imperativa. Declarativa: describes el estado deseado ("debe haber 3 contenedores de esta imagen") y la herramienta calcula qué hacer para llegar a él. Imperativa: das las órdenes paso a paso ("arranca un contenedor, luego otro..."). Terraform, Kubernetes y los módulos de Ansible son declarativos; un script de Bash es imperativo. Lo declarativo es idempotente: aplicarlo varias veces da el mismo resultado.
    • Con agente o sin agente. Puppet y Chef instalan un programa (agente) en cada servidor gestionado; Ansible se conecta por SSH sin instalar nada.
    • Push o pull. En push, un servidor central envía los cambios (Ansible, un pipeline que ejecuta docker run en el servidor). En pull, un agente en el destino consulta periódicamente el estado deseado y lo aplica (Puppet, Argo CD, Flux). El modelo pull es la base de GitOps.
    • Arquitectura: cliente/servidor (Docker CLI y el demonio dockerd), sin demonio (Podman), controlador con bucle de reconciliación (Kubernetes).
    • Licencia y gobierno: libre (Apache 2.0, MIT, GPL), de código disponible con restricciones o propietaria; mantenida por una fundación, por una empresa o por la comunidad. Importa: en 2023 HashiCorp cambió la licencia de Terraform a BSL, y la comunidad creó OpenTofu bajo la Linux Foundation.

    3. Las herramientas principales en detalle

    Git y las plataformas de código

    Git (Linus Torvalds, 2005) es un sistema de control de versiones distribuido: cada copia del repositorio tiene el historial completo. Conceptos: commit, rama, fusión, etiqueta, remoto. Las plataformas (GitHub, GitLab, Gitea) añaden alojamiento, pull requests con revisión, gestión de permisos, issues, CI/CD integrado y registro de paquetes. Son el punto de partida de todo el flujo DevOps: el repositorio es la fuente única de verdad del código, de la infraestructura y de la configuración.

    Docker

    Popularizó los contenedores en 2013. Su arquitectura:

    docker (CLI) ──API REST──► dockerd (demonio) ──► containerd ──► runc ──► contenedor
                                  │
                                  └── BuildKit (construcción de imágenes)

    La CLI habla con el demonio dockerd, que se ejecuta como root; este delega en containerd (gestión del ciclo de vida de contenedores e imágenes) y en runc (el que realmente crea el contenedor con namespaces y cgroups, según la especificación OCI). Docker Compose define aplicaciones de varios contenedores en un fichero YAML. Docker Desktop tiene licencia de pago para empresas grandes; Docker Engine en Linux es libre.

    Podman, Buildah y Kaniko

    Podman (Red Hat) es compatible con la CLI de Docker (alias docker=podman funciona en la mayoría de casos) pero no tiene demonio: cada contenedor es un proceso hijo del usuario, y funciona sin root (rootless) por defecto, lo que mejora la seguridad. Agrupa contenedores en pods como Kubernetes y se integra con systemd (Quadlet). Buildah construye imágenes sin demonio, y Kaniko las construye dentro de un contenedor sin privilegios, útil en pipelines sobre Kubernetes.

    Registros

    Docker Hub es el registro público por defecto (con límites de descargas para usuarios anónimos). GitHub Container Registry (ghcr.io) está integrado con los repositorios y los permisos de GitHub. Harbor (CNCF) es un registro autoalojado con control de acceso por proyectos, escaneo de vulnerabilidades integrado, firma de imágenes, replicación entre registros y políticas de retención.

    GitHub Actions, GitLab CI y Jenkins

    Herramientas de CI/CD. GitHub Actions define workflows en YAML dentro del repositorio (.github/workflows/), disparados por eventos (push, pull request, programación); los trabajos se ejecutan en máquinas (runners) de GitHub o propias, y reutilizan acciones del Marketplace. GitLab CI es similar con el fichero .gitlab-ci.yml. Jenkins es el veterano libre: un servidor autoalojado, extensible con miles de plugins, con pipelines escritos en Groovy (Jenkinsfile); muy flexible, pero exige mantenerlo.

    Argo CD y Flux: GitOps

    Agentes que se ejecutan dentro de un clúster Kubernetes y comparan continuamente lo que hay en el clúster con lo declarado en un repositorio Git. Si alguien cambia algo a mano o se fusiona un cambio en Git, lo reconcilian. El despliegue se hace con un pull request: Git es la fuente de verdad del estado de producción.

    Terraform / OpenTofu

    Infraestructura como código declarativa. Se describen recursos en lenguaje HCL y la herramienta, mediante proveedores (plugins para AWS, Azure, Proxmox, Docker, GitHub...), calcula un plan de cambios y lo aplica. Guarda un estado con lo que ha creado. Lo usaremos en la unidad 6.

    Ansible

    Gestión de la configuración y automatización, sin agente, por SSH, en modo push. Se escriben playbooks en YAML con tareas que usan módulos idempotentes. Unidad 7.

    Kubernetes

    Orquestador de contenedores creado por Google (2014) y donado a la CNCF. Declarativo: se describen objetos (Deployment, Service, Ingress) y sus controladores trabajan en un bucle de reconciliación para que la realidad coincida con lo declarado: reinician contenedores caídos, reparten la carga entre nodos, escalan y actualizan sin corte. Es el estándar de facto para ejecutar contenedores a escala; lo veréis en el módulo 5166.

    Prometheus y Grafana

    Prometheus recoge métricas consultando (modelo pull, scraping) cada cierto tiempo un punto HTTP /metrics de cada servicio, las guarda como series temporales y evalúa reglas de alerta. Grafana dibuja paneles con esas métricas. Unidad 7.

    1. Por qué validar antes de desplegar

    Cada cambio que llega a producción puede introducir errores funcionales, código difícil de mantener, vulnerabilidades o dependencias con fallos conocidos. Revisarlo todo a mano es imposible cuando se despliega a menudo. La solución DevOps es automatizar las comprobaciones y ejecutarlas en cada cambio, lo antes posible: es el principio de desplazar a la izquierda (shift left), porque en un diagrama del ciclo de vida de izquierda a derecha, las comprobaciones se mueven hacia el principio, donde corregir es más barato. Integrar la seguridad en todo el ciclo es lo que se llama DevSecOps.

    2. Herramientas de calidad del código

    Formateadores y linters

    • Formateadores: reescriben el código con un estilo uniforme (Black o ruff format en Python, Prettier en JavaScript). Eliminan discusiones sobre estilo en las revisiones.
    • Linters: analizan el código sin ejecutarlo en busca de errores probables, malas prácticas y problemas de estilo: variables sin usar, importaciones que faltan, comparaciones sospechosas, complejidad excesiva. Ejemplos: Ruff y Pylint (Python), ESLint (JavaScript), hadolint (Dockerfile), ShellCheck (Bash), yamllint, ansible-lint, terraform fmt y terraform validate.

    Pruebas automáticas

    TipoQué pruebaVelocidadHerramientas
    UnitariasUna función o clase aisladaMilisegundospytest, JUnit, Jest
    De integraciónVarios componentes juntos (aplicación + base de datos)Segundospytest con contenedores (Testcontainers), Docker Compose
    Extremo a extremo (E2E)El sistema completo como lo usaría una personaMinutosPlaywright, Selenium, Cypress
    De rendimiento y cargaComportamiento con muchos usuariosMinutosk6, JMeter, Locust

    La pirámide de pruebas recomienda muchas pruebas unitarias, bastantes de integración y pocas E2E, porque estas son lentas y frágiles. La cobertura mide qué porcentaje del código se ejecuta durante las pruebas (pytest-cov, JaCoCo); una cobertura alta no garantiza buenas pruebas, pero una baja indica código sin probar.

    Análisis estático de calidad

    SonarQube (autoalojado) y SonarQube Cloud (SaaS, gratuito para proyectos públicos) analizan el código en decenas de lenguajes y clasifican los problemas en fiabilidad (bugs), mantenibilidad (code smells, deuda técnica, complejidad, duplicación) y seguridad (vulnerabilidades y puntos calientes de seguridad a revisar). Su concepto central es el quality gate: un conjunto de condiciones que debe cumplir el código nuevo para que el análisis se considere aprobado (por ejemplo, cobertura ≥ 80 %, duplicación ≤ 3 %, ninguna vulnerabilidad nueva). Si no se cumple, el pipeline falla y el cambio no se puede fusionar. Aplicarlo al código nuevo evita que la deuda crezca sin obligar a arreglar todo lo antiguo de golpe.

    Revisión de código

    La revisión por otra persona en el pull request sigue siendo imprescindible: detecta problemas de diseño y de lógica que ninguna herramienta ve. Las herramientas automáticas liberan a quien revisa de lo mecánico.

    Conceptos que hay que conocer

    • CVE (Common Vulnerabilities and Exposures): identificador público de una vulnerabilidad conocida, como CVE-2021-44228 (Log4Shell). Las herramientas SCA y de imágenes buscan CVE en las versiones que usamos.
    • CVSS: puntuación de gravedad de 0 a 10 (baja, media, alta, crítica). Ayuda a priorizar, aunque hay que valorar si la parte vulnerable se usa realmente.
    • Bases de datos de vulnerabilidades: NVD (EE. UU.), GitHub Advisory Database, OSV.
    • CWE: catálogo de tipos de debilidad (por ejemplo, CWE-89 inyección SQL). El OWASP Top 10 resume los riesgos más frecuentes en aplicaciones web.
    • SBOM (Software Bill of Materials): lista de todos los componentes y versiones que contiene un software o una imagen, en formatos estándar como SPDX o CycloneDX. Permite saber en minutos si estamos afectados por una nueva vulnerabilidad. Herramientas: Syft, Trivy.
    • Falsos positivos: avisos que no son un problema real. Se revisan y se marcan justificadamente; ignorarlos sin más hace que se pierda la confianza en la herramienta.
    • Firma de imágenes (cosign, de Sigstore): permite comprobar que una imagen la construyó nuestro pipeline y no se ha manipulado.

    Integraciones y dependencias externas

    Además de librerías, las aplicaciones dependen de integraciones: API de terceros, servicios de pago, proveedores de SMS. Se validan con pruebas de contrato (el formato de las peticiones y respuestas no cambia sin avisar), pruebas de integración contra entornos de prueba del proveedor o simulaciones (mocks), y revisando la seguridad de la conexión (TLS, credenciales en secretos). Lo trabajaremos en la sesión 29.

    1. Principios de control de acceso

    Autenticación, autorización y auditoría

    • Autenticación: comprobar quién eres (contraseña, doble factor, clave SSH, token).
    • Autorización: decidir qué puedes hacer (permisos).
    • Auditoría (accounting): registrar qué has hecho, para poder revisarlo.

    Mínimo privilegio

    Cada persona y cada proceso debe tener solo los permisos que necesita, solo sobre los recursos que necesita y solo durante el tiempo que los necesita. Si una cuenta se ve comprometida, el daño queda limitado a lo que esa cuenta podía hacer. Es el principio de seguridad más importante de esta unidad y de la siguiente.

    Control de acceso basado en roles (RBAC)

    No se asignan permisos persona a persona: se definen roles (conjuntos de permisos) y grupos (conjuntos de personas), y se asigna un rol a un grupo sobre un recurso. Cuando alguien entra en el equipo, se le añade al grupo; cuando cambia de puesto, se le mueve; cuando se va, se le quita. Así la gestión es sencilla y auditable. Es el ciclo de vida de las identidades: alta, cambio y baja (joiner, mover, leaver).

    Separación de funciones

    Las acciones críticas no debe poder completarlas una sola persona: quien escribe un cambio no debe poder aprobarlo y desplegarlo a producción sin que otra persona lo revise. Protege frente a errores y frente a abusos.

    Identidades de máquina

    No solo las personas acceden: también los procesos (el pipeline de CI/CD, Terraform, Ansible). Necesitan sus propias credenciales (cuentas de servicio, tokens, claves de despliegue) con permisos mínimos, nunca las credenciales personales de alguien del equipo.

    2. Permisos en GitHub

    Organizaciones

    Una organización agrupa repositorios y personas de un proyecto o empresa. Roles de organización:

    • Owner (propietario): control total, incluida la facturación y la seguridad. Debe haber al menos dos, y pocos.
    • Member (miembro): participa según los permisos de sus equipos.
    • Colaborador externo: persona ajena a la organización con acceso a repositorios concretos.

    En la configuración de la organización se fijan los permisos base de los miembros sobre todos los repositorios (recomendado: No permission o Read), si pueden crear repositorios y si se exige doble factor.

    Equipos y roles de repositorio

    Los equipos (teams) agrupan miembros. A cada equipo se le da un rol sobre cada repositorio:

    WriteAdemás, crear ramas, hacer push y fusionar pull requests (si las reglas lo permiten)Desarrollo

    Entornos (environments)

    Un entorno de GitHub representa un destino de despliegue (revision, produccion). Cada entorno tiene:

    • Secretos y variables propios: la contraseña de la base de datos de producción solo la ve un trabajo que despliega en producción.
    • Reglas de protección: revisores obligatorios (el trabajo queda en pausa hasta que una persona o equipo autorizado lo aprueba), temporizador de espera, ramas o etiquetas permitidas (solo se despliega a producción desde main) y evitar que quien lanzó el despliegue se lo apruebe a sí mismo.
    • Historial de despliegues: qué versión está en cada entorno y quién la aprobó.
    jobs:

    2. Autorización: qué se puede hacer con el código

    Reglas de protección (rulesets)

    Los rulesets de GitHub (sustitutos modernos de las antiguas branch protection rules) aplican políticas sobre ramas o etiquetas que coinciden con un patrón, a nivel de repositorio o de toda la organización. Las reglas más importantes para la rama main:

    Restringir borradosQue alguien borre la rama
    Bloquear force pushReescribir el historial publicado

    Aprobaciones requeridasFusionar sin N revisiones aprobadas

    Los rulesets permiten definir excepciones (bypass list) para roles o apps concretos, y un modo Evaluate para probar una regla sin aplicarla. También se pueden proteger las etiquetas de versión (v*) para que nadie las mueva o borre.

    CODEOWNERS

    El fichero .github/CODEOWNERS asigna responsables a rutas del repositorio. Cuando un pull request toca esas rutas, se solicita automáticamente su revisión y, con la regla correspondiente, es obligatoria:

    .github/CODEOWNERS

    # La última coincidencia gana
*                  @citaprevia-NOMBRES/desarrollo
Dockerfile         @citaprevia-NOMBRES/operaciones

/ansible/          @citaprevia-NOMBRES/operaciones

/.github/CODEOWNERS @citaprevia-NOMBRES/operaciones

    Así, un cambio en el pipeline o en la infraestructura siempre lo revisa operaciones, aunque lo proponga desarrollo.

    Estrategias de ramas

    • GitHub flow y desarrollo basado en troncal (trunk-based): una rama principal siempre desplegable y ramas cortas (horas o pocos días) que se fusionan mediante pull request. Es la recomendada para CI/CD.
    • Git flow: ramas develop, release, hotfix... Pensada para versiones planificadas; más compleja y con integración menos continua.

    Con cualquiera de ellas, la rama que se despliega debe estar protegida.

    3. Otros parámetros de seguridad del repositorio

    • Visibilidad: público, privado o interno. Un repositorio público nunca debe contener secretos ni datos personales.
    • Secret scanning y push protection: GitHub detecta credenciales conocidas en el código y, con push protection, rechaza el push que las contiene (sesión 28).
    • Alertas de Dependabot y notificación privada de vulnerabilidades.
    • Fichero SECURITY.md: cómo comunicar una vulnerabilidad.
    • Registro de auditoría de la organización: quién cambió permisos, reglas o secretos y cuándo.
    • Revisión periódica de miembros, colaboradores externos, claves de despliegue y tokens autorizados.

    2. Pruebas automáticas con pytest

    pytest busca ficheros test_*.py y ejecuta las funciones test_*. Cada prueba sigue el esquema preparar, actuar, comprobar (arrange, act, assert). Flask ofrece un cliente de pruebas que simula peticiones HTTP sin arrancar un servidor:

    test_app.py

    import pytest
from app import app

@pytest.fixture
def cliente():
    app.config["TESTING"] = True
    return app.test_client()

def test_salud(cliente):
    r = cliente.get("/salud")
    assert r.status_code == 200
    assert r.get_json()["estado"] == "ok"

def test_citas_devuelve_lista(cliente):
    r = cliente.get("/citas")
    assert r.status_code == 200
    assert isinstance(r.get_json(), list)

@pytest.mark.parametrize("ruta", ["/no-existe", "/citas/extra"])
def test_rutas_inexistentes(cliente, ruta):
    assert cliente.get(ruta).status_code == 404
    • Una fixture prepara lo que necesitan las pruebas (aquí, el cliente) y se inyecta por nombre.
    • parametrize ejecuta la misma prueba con varios datos.
    • La cobertura con pytest --cov=. --cov-report=term-missing --cov-report=xml indica qué líneas no se han ejecutado; el XML lo lee SonarQube.
    • Una buena prueba comprueba también los casos de error: identificadores que no existen, datos mal formados, límites.

    CE 5f

    Objetivos de la sesión

    • Explicar por qué las comprobaciones de seguridad deben ser periódicas y no solo al cambiar el código.
    • Conocer el funcionamiento de CodeQL, de la detección de secretos y del escaneo con Trivy.

    • Definir un proceso de clasificación y corrección de hallazgos con plazos según la gravedad.

    1. Por qué comprobar de forma periódica

    El código que ayer era seguro puede no serlo hoy sin que nadie lo toque: cada día se publican decenas de CVE nuevas que afectan a librerías, a imágenes base y a patrones de código. Además, las herramientas mejoran sus reglas y detectan problemas que antes no veían. Por eso, además de validar cada cambio (sesión 27), hay que ejecutar las comprobaciones de seguridad de forma periódica sobre la rama principal y sobre lo que está desplegado.

    El ejemplo clásico es Log4Shell (CVE-2021-44228, diciembre de 2021): una vulnerabilidad crítica en la librería de registros Log4j de Java, presente en miles de aplicaciones que llevaban años sin cambiar. Las organizaciones que tenían escaneos periódicos y SBOM supieron en horas qué sistemas estaban afectados; las demás tardaron semanas.

    2. CodeQL: análisis estático de seguridad

    CodeQL es el motor SAST de GitHub, gratuito para repositorios públicos. Funciona en dos fases:

    1. Extracción: convierte el código en una base de datos que representa su estructura (sintaxis, flujo de datos, flujo de control). En lenguajes compilados, observa la compilación.
    2. Consultas: ejecuta consultas escritas en el lenguaje QL que buscan patrones de vulnerabilidad. La más importante es el análisis de flujo de datos contaminados (taint tracking): sigue un dato que entra desde el usuario (un parámetro de la petición, la "fuente") hasta un punto peligroso (una consulta SQL, una orden del sistema, el "sumidero") sin pasar por una validación o saneamiento.

    Hay conjuntos de consultas predefinidos: default (alta precisión) y security-extended (más consultas, más falsos positivos). Soporta Python, JavaScript/TypeScript, Java, C#, C/C++, Go, Ruby, Swift, Kotlin y las propias GitHub Actions. Se activa de dos formas: configuración por defecto (un clic en Settings → Code security) o avanzada (un workflow que se puede personalizar y programar).

    3. Detección de secretos

    • Secret scanning de GitHub: busca en todo el historial del repositorio patrones de credenciales de cientos de proveedores (AWS, Azure, Google, Slack, Stripe, tokens de GitHub...) y avisa. En repositorios públicos, además, avisa al proveedor para que revoque la credencial.
    • Push protection: detecta la credencial antes de que llegue al repositorio y rechaza el push. Es mucho mejor prevenir que detectar: un secreto que se ha publicado, aunque se borre en el siguiente commit, sigue en el historial y debe considerarse comprometido.
    • gitleaks y TruffleHog: herramientas libres que buscan secretos en el historial con reglas y entropía; se pueden usar en local (pre-commit), en CI y en otras plataformas. Detectan también secretos genéricos (contraseñas, claves) que no siguen un patrón de proveedor.

    Si se filtra un secreto: 1) revocarlo o rotarlo inmediatamente en el servicio; 2) revisar los registros para ver si se ha usado; 3) después, si se quiere, limpiarlo del historial (git filter-repo). Borrarlo del código no sirve de nada si no se revoca.

    4. Trivy

    Trivy (Aqua Security, libre) es un escáner "todo en uno":

    • trivy fs .: dependencias declaradas en el repositorio (requirements.txt, package-lock.json...), secretos y configuraciones.
    • trivy config .: configuraciones inseguras en Dockerfile, Terraform, Kubernetes.
    • trivy image IMAGEN: paquetes del sistema operativo y librerías dentro de una imagen.
    • trivy image --format cyclonedx: genera el SBOM.

    Sus resultados se pueden exportar en SARIF (Static Analysis Results Interchange Format), un formato JSON estándar que GitHub muestra en la pestaña Security → Code scanning junto a los de CodeQL. Así todos los hallazgos quedan en un único sitio, con su historial.

    5. Programar ejecuciones: schedule

    El evento schedule usa la sintaxis de cron (en hora UTC):

    ┌───────── minuto (0-59)
│ ┌─────── hora (0-23)
│ │ ┌───── día del mes (1-31)
│ │ │ ┌─── mes (1-12)
│ │ │ │ ┌─ día de la semana (0-6, 0 = domingo)
│ │ │ │ │
30 2 * * 1      → cada lunes a las 02:30 UTC
0 4 * * *       → todos los días a las 04:00 UTC

    Los workflows programados solo se ejecutan sobre la rama por defecto, y GitHub los desactiva en repositorios públicos sin actividad durante 60 días.

    Validar dependencias e integración antes de desplegar

    CE 5g

    Objetivos de la sesión

    • Identificar los riesgos de las dependencias externas y de la cadena de suministro del software.
    • Fijar y actualizar dependencias de forma controlada con ficheros de bloqueo y Dependabot.
    • Validar antes del despliegue la seguridad, la licencia y la funcionalidad de las dependencias y de las integraciones.
    • Construir un pipeline que construye la imagen, la escanea, prueba su integración con el resto de componentes y solo entonces la publica.

    1. El problema de las dependencias

    Una aplicación moderna tiene muy poco código propio: la mayor parte son dependencias. Nuestra pequeña cita-previa-app declara dos (Flask y Gunicorn), pero al instalarlas se descargan también sus dependencias transitivas (Werkzeug, Jinja2, MarkupSafe, itsdangerous, click, blinker, packaging...), y la imagen de contenedor añade cientos de paquetes del sistema operativo. Cada una de ellas es código de terceros que se ejecuta con los permisos de nuestra aplicación.

    Riesgos

    • Vulnerabilidades conocidas (CVE) en versiones concretas.
    • Paquetes maliciosos: publicados con nombres parecidos a otros populares (typosquatting: reqeusts en lugar de requests), o legítimos cuya cuenta de publicación ha sido robada.
    • Ataques a la cadena de suministro: introducir código malicioso en un proyecto de confianza. Casos reales: event-stream (npm, 2018), el sistema de compilación de SolarWinds (2020) y la puerta trasera en xz-utils (2024), descubierta por casualidad poco antes de llegar a las versiones estables de muchas distribuciones Linux tras años de preparación por parte del atacante.
    • Proyectos abandonados que ya no reciben correcciones.
    • Cambios incompatibles al actualizar, que rompen la aplicación.
    • Licencias incompatibles con el uso que queremos hacer (por ejemplo, una licencia copyleft fuerte en un producto que no se quiere publicar).

    2. Controlar las versiones

    Rangos, versiones fijadas y ficheros de bloqueo

    El versionado semántico (MAYOR.MENOR.PARCHE) indica el tipo de cambio: parche, correcciones; menor, novedades compatibles; mayor, cambios incompatibles. En requirements.txt podemos declarar rangos (flask==3.1.*), pero entonces dos construcciones en días distintos pueden instalar versiones diferentes: las construcciones no son reproducibles.

    La solución es separar lo que queremos (dependencias directas con rangos, en requirements.in) de lo que instalamos exactamente (todas, incluidas las transitivas, con versión exacta y hash, en un fichero de bloqueo):

    pip install pip-tools
pip-compile --generate-hashes requirements.in -o requirements.txt
pip install --require-hashes -r requirements.txt

    Con los hashes, pip rechaza cualquier paquete cuyo contenido no coincida, aunque alguien lo sustituya en el repositorio de paquetes. Otros ecosistemas tienen su equivalente: package-lock.json (npm), poetry.lock, uv.lock, go.sum. En Docker, lo mismo se consigue fijando la imagen base por digest (python:3.12-slim@sha256:...).

    Actualizar de forma controlada: Dependabot

    Fijar versiones no significa no actualizar nunca: significa actualizar de forma deliberada y probada. Dependabot revisa periódicamente las dependencias y abre pull requests con las actualizaciones; cada PR pasa por todo el pipeline de calidad y seguridad antes de fusionarse. Tiene dos funciones:

    • Actualizaciones de seguridad: PR automático cuando hay una alerta de vulnerabilidad.
    • Actualizaciones de versión: PR periódicos para mantener todo al día, configurados en .github/dependabot.yml.

    .github/dependabot.yml

    version: 2
updates:
  - package-ecosystem: pip
    directory: "/"
    schedule:
      interval: weekly
    groups:
      menores-y-parches:
        update-types: [minor, patch]
  - package-ecosystem: docker          # imagen base del Dockerfile
    directory: "/"
    schedule:
      interval: weekly

    schedule:
      interval: weekly

    4. Validar la integración antes de desplegar

    Que cada pieza pase sus pruebas no garantiza que funcionen juntas. Las pruebas de integración comprueban la aplicación con sus componentes reales: la imagen de contenedor tal como se desplegará, su base de datos, su proxy, sus variables de entorno. En un pipeline de contenedores:

    1. Construir la imagen una sola vez.
    2. Escanearla: si tiene vulnerabilidades críticas corregibles, se para.
    3. Arrancarla con la configuración de un entorno (y sus dependencias, con Docker Compose) y esperar a que el healthcheck diga que está sana.
    4. Pruebas de humo (smoke tests) e integración contra el contenedor en marcha: responde en /salud, devuelve citas, devuelve 404 donde debe, las cabeceras son correctas, no se ejecuta como root.
    5. Solo si todo pasa, publicar la imagen en el registro con su versión y el hash del commit, junto con su SBOM.

    Aplicación de ejemplo cita-previa-app

    app.py

    from flask import Flask, jsonify
import os

app = Flask(__name__)
CITAS = [{"id": 1, "paciente": "Ana", "dia": "2027-01-15"}]

@app.route("/salud")
def salud():
    return jsonify(estado="ok", entorno=os.getenv("ENTORNO", "local"))

@app.route("/citas")
def citas():
    return jsonify(CITAS)

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=int(os.getenv("PORT", 8000)))
