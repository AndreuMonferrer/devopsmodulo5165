Unidad 5. Repositorios de código, calidad y seguridad

Crear y proteger el acceso a los repositorios y comprobar automáticamente la calidad y la seguridad de cada cambio antes de desplegarlo.

Unidad 5 de 7, 7 sesiones, 14 horas

Resultado de aprendizaje 5

Crea el acceso a los repositorios de código de infraestructura y/o servicios, comprobando las herramientas de gestión y de validación de la calidad y seguridad de las modificaciones de código fuente previas al despliegue.

Empieza la parte técnica del módulo. Antes de desplegar nada hay que tener bajo control el código: quién puede leerlo y cambiarlo, qué cambios se aceptan y con qué comprobaciones. En esta unidad montamos, por parejas, una organización de GitHub con equipos y permisos, un repositorio protegido con la aplicación de ejemplo y un conjunto de flujos de GitHub Actions que validan calidad (pruebas, linter, SonarQube Cloud), seguridad (CodeQL, detección de secretos) y dependencias (Dependabot, revisión de dependencias, escaneo de la imagen).

Las dos primeras sesiones son de panorama de herramientas; el resto, laboratorio. Lo que construyáis aquí se reutiliza en las unidades 6 y 7.

Requisito: repositorios públicos. Así CodeQL, la revisión de dependencias y SonarQube Cloud son gratuitos. No subáis nunca contraseñas ni datos reales.

CE 5aCE 5bCE 5c

Inicio10′Prueba escrita30′Introducción15′Laboratorio50′Cierre15′

Qué vas a saber hacer al terminar

  • Crear una organización con equipos y roles que permitan y limiten.
  • Definir entornos de revisión y producción con su propio control de acceso.

Introducción del tema

Principio de mínimo privilegio

Cada persona y cada proceso debe tener solo los permisos que necesita, durante el tiempo que los necesita. Se gestiona por grupos o perfiles, no persona a persona.

En GitHub

  • Organización con roles de propietario (owner) y miembro.
  • Equipos (teams) con un rol en cada repositorio: Read, Triage, Write, Maintain o Admin.
  • Entornos (environments) como revision y produccion: cada uno con sus secretos y reglas de protección (revisores obligatorios, espera, ramas permitidas). Un workflow que despliega a producción queda en pausa hasta que alguien autorizado lo aprueba.

Y en la infraestructura

El mismo principio se aplica en Proxmox (usuarios, grupos, roles como PVEVMUser, permisos por pool) y en la nube (IAM: usuarios, grupos, roles y políticas). Lo aplicaremos a fondo en la unidad 6.

Actividad

Prueba escrita (30′) sobre los criterios a y b.

Laboratorio (50′), por parejas. Diseñad primero una matriz de accesos y después configuradla:

  1. Cread una organización gratuita en GitHub (citaprevia-NOMBRES) e invitad a vuestra pareja y al profesor.
  2. Cread los equipos desarrollo (Write), operaciones (Maintain) y auditoria (Read). Cada miembro en al menos uno.
  3. Cread el repositorio público cita-previa-app con los ficheros de la pestaña Recursos y asignad los equipos.
  4. En Settings, Environments: cread revision (sin restricciones) y produccion (revisor obligatorio: equipo operaciones; solo desde la rama main). Añadid un secreto de ejemplo distinto en cada uno (DB_PASSWORD).
  5. Documentad en ACCESOS.md la matriz: quién puede leer, cambiar código, aprobar despliegues a producción y administrar.
Puesta en común

Probamos los límites: ¿puede alguien del equipo auditoría abrir un pull request? ¿Y aprobar un despliegue a producción?

Acceso seguro al código fuente: políticas y protección de ramas

CE 5cCE 5d

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Configurar el acceso al repositorio con parámetros de seguridad y políticas por usuarios y grupos.
  • Proteger la rama principal con reglas que obliguen a revisar y validar.

Introducción del tema

Autenticación: quién eres

  • Doble factor (2FA) obligatorio en la organización.
  • Claves SSH para Git desde el portátil (una por persona y equipo), preferiblemente ed25519.
  • Tokens de acceso personal de grano fino: limitados a unos repositorios, unos permisos y una fecha de caducidad. Nunca los clásicos con acceso a todo.
  • Deploy keys para que un servidor lea un único repositorio.

Autorización: qué puedes hacer

  • Rulesets (reglas) sobre ramas: exigir pull request, número de aprobaciones, comprobaciones de estado superadas, historial lineal, bloquear force-push y borrado.
  • CODEOWNERS: quién debe revisar obligatoriamente cada ruta del repositorio.
  • Commits firmados para garantizar la autoría.

.github/CODEOWNERS

*                 @citaprevia-NOMBRES/desarrollo
Dockerfile        @citaprevia-NOMBRES/operaciones
.github/          @citaprevia-NOMBRES/operaciones

Actividad

  1. (15′) Activad 2FA en vuestra cuenta y exigidlo en la organización.
  2. (15′) En Ubuntu MATE: ssh-keygen -t ed25519 -C "correo", añadid la clave pública a GitHub y comprobad con ssh -T git@github.com. Clonad el repositorio por SSH.
  3. (20′) Cread un ruleset para main: pull request obligatorio con 1 aprobación, descartar aprobaciones al añadir commits, revisión de CODEOWNERS obligatoria, bloquear force-push y borrado. Añadid el fichero CODEOWNERS.
  4. (10′) Cread un token de grano fino de solo lectura sobre un repositorio y 7 días de caducidad; probadlo con curl contra la API y revocadlo.
  5. (15′) Intentad saltaros las reglas: push directo a main, fusionar sin aprobación, force-push. Documentad qué mensaje da GitHub en cada caso en ACCESOS.md.
Puesta en común

Repasamos qué parámetros de seguridad tiene cada repositorio y quién los puede cambiar.

Evidencia de evaluación

Repositorio con 2FA, SSH, ruleset y CODEOWNERS, y pruebas documentadas (CE 5d, completa 5c).

Validar cada cambio: pruebas y análisis de calidad automáticos

CE 5e

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Ejecutar pruebas de calidad en cada pull request mediante GitHub Actions.
  • Integrar SonarQube Cloud con un quality gate.
  • Documentar la validación de una modificación.

Introducción del tema

Anatomía de un workflow de GitHub Actions

Un fichero YAML en .github/workflows/ con: eventos que lo disparan (on), trabajos (jobs) que se ejecutan en una máquina (runs-on) y pasos (steps) que son comandos o acciones reutilizables.

.github/workflows/calidad.yml

name: Calidad
on:
  pull_request:
  push:
    branches: [main]
jobs:
  pruebas:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0          # SonarQube Cloud necesita el historial
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: pip install -r requirements-dev.txt
      - name: Linter
        run: ruff check .
      - name: Pruebas con cobertura
        run: pytest --cov=. --cov-report=xml
      - name: Análisis SonarQube Cloud
        uses: SonarSource/sonarqube-scan-action@v5
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}

sonar-project.properties

sonar.organization=citaprevia-nombres
sonar.projectKey=citaprevia-nombres_cita-previa-app
sonar.python.coverage.reportPaths=coverage.xml
sonar.qualitygate.wait=true

El quality gate define las condiciones mínimas del código nuevo (cobertura, duplicación, sin bugs ni vulnerabilidades nuevas). Si no se cumple, el check falla y el ruleset impide fusionar.

Actividad

  1. (15′) Entrad en SonarQube Cloud con vuestra cuenta de GitHub, importad la organización y el proyecto, desactivad el análisis automático y generad el token. Guardadlo como secreto SONAR_TOKEN del repositorio.
  2. (20′) Cread en una rama el workflow y el fichero de propiedades. Abrid un pull request y corregid hasta que todo esté en verde.
  3. (10′) Añadid los checks pruebas y el quality gate como obligatorios en el ruleset de main.
  4. (20′) Modificación a validar: añadid una ruta /citas/<id> que devuelva una cita o 404, con sus pruebas. Probad primero sin pruebas (¿qué dice el quality gate de la cobertura?) y luego con ellas.
  5. (10′) Documentad en docs/validacion.md: cambio realizado, herramientas ejecutadas, resultados (capturas), problemas encontrados y cómo se resolvieron.
Puesta en común

Revisamos un pull request de cada pareja en el proyector: checks, comentarios de SonarQube Cloud y aprobación.

Evidencia de evaluación

Workflow de calidad en verde, quality gate obligatorio y docs/validacion.md (CE 5e).

Notas para el docente

Comprobaciones de seguridad periódicas

CE 5f

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Ejecutar análisis de seguridad del código con herramientas específicas.
  • Programarlos para que se ejecuten de forma periódica y no solo cuando hay cambios.

Introducción del tema

¿Por qué periódicamente?

Cada día se publican vulnerabilidades nuevas. Un código que ayer estaba limpio puede ser vulnerable hoy sin que nadie lo toque. Por eso, además de analizar cada cambio, se programa un análisis completo, por ejemplo cada noche o cada semana, con el evento schedule y la sintaxis de cron.

# minuto hora día-mes mes día-semana   (hora UTC)
- cron: "0 3 * * 1"      # cada lunes a las 03:00 UTC

.github/workflows/seguridad.yml

name: Seguridad
on:
  pull_request:
  schedule:
    - cron: "0 3 * * 1"
  workflow_dispatch:           # permite lanzarlo a mano
permissions:
  contents: read
  security-events: write       # necesario para subir resultados de CodeQL
jobs:
  codeql:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: github/codeql-action/init@v3
        with:
          languages: python
      - uses: github/codeql-action/analyze@v3
  secretos-y-ficheros:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Secretos en todo el historial (gitleaks)
        run: docker run --rm -v "$PWD":/repo zricethezav/gitleaks:latest detect --source=/repo -v
      - name: Configuración insegura y vulnerabilidades (Trivy)
        run: docker run --rm -v "$PWD":/src aquasec/trivy:latest fs --scanners vuln,secret,misconfig --exit-code 1 --severity HIGH,CRITICAL /src

Además, en Settings, Code security se activan el secret scanning y la push protection, que bloquea el push si detecta un token conocido.

Buena práctica. Dad a cada workflow solo los permisos que necesita (permissions) y, en entornos profesionales, fijad las acciones de terceros por su hash de commit en lugar de por etiqueta: ha habido ataques a la cadena de suministro que modificaban etiquetas de acciones populares.

Actividad

  1. (10′) Activad secret scanning, push protection y Dependabot alerts en la organización.
  2. (20′) Añadid el workflow de seguridad y ejecutadlo a mano (Run workflow). Revisad la pestaña Security.
  3. (20′) Introducid en una rama un fallo que detecte CodeQL (por ejemplo, subprocess.run(request.args["cmd"], shell=True)) y un fichero con un token falso con formato real. Observad qué herramienta lo detecta y en qué momento (push protection, PR, análisis).
  4. (10′) Añadid a Trivy un .trivyignore justificado si aparece algún falso positivo.
  5. (15′) Documentad en docs/seguridad.md: herramientas, periodicidad elegida y por qué, un ejemplo de hallazgo y su corrección.
Puesta en común

¿Qué hacemos cuando el análisis del lunes falla en main sin que nadie haya cambiado nada?

Evidencia de evaluación

Validar dependencias e integración antes de desplegar. Entrega de la unidad

CE 5g

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Detectar dependencias vulnerables o desactualizadas y actualizarlas de forma controlada.
  • Comprobar que la imagen del contenedor es segura y se integra con el resto antes de publicarla.

Introducción del tema

La mayor parte de tu código no lo has escrito tú

Una aplicación moderna tiene decenas o cientos de dependencias directas y transitivas. Los ataques a la cadena de suministro (Log4Shell en 2021, la puerta trasera de xz-utils en 2024) muestran que validar dependencias es imprescindible.

  • Dependabot alerts avisa de dependencias con CVE conocidos; security updates abre PR para corregirlas.
  • Dependabot version updates propone actualizaciones periódicas de versión.
  • Dependency review bloquea un PR que introduce una dependencia vulnerable.
  • Escaneo de la imagen y prueba de integración: construir la imagen, arrancarla y comprobar que responde, antes de publicarla en el registro.

.github/dependabot.yml

version: 2
updates:
  - package-ecosystem: pip
    directory: "/"
    schedule: { interval: weekly }
  - package-ecosystem: docker
    directory: "/"
    schedule: { interval: weekly }
  - package-ecosystem: github-actions
    directory: "/"
    schedule: { interval: weekly }

.github/workflows/predespliegue.yml

name: Predespliegue
on: pull_request
permissions:
  contents: read
jobs:
  dependencias:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/dependency-review-action@v4
        with: { fail-on-severity: high }
      - run: pipx run pip-audit -r requirements.txt
  imagen:
    needs: dependencias
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t cita-previa:${{ github.sha }} .
      - name: Escaneo de la imagen
        run: |
          docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy:latest             image --exit-code 1 --severity CRITICAL cita-previa:${{ github.sha }}
      - name: Prueba de integración
        run: |
          docker run -d --name app -p 8000:8000 -e ENTORNO=ci cita-previa:${{ github.sha }}
          sleep 5
          curl --fail http://localhost:8000/salud
          curl --fail http://localhost:8000/citas

Actividad

  1. (15′) Añadid dependabot.yml y el workflow de predespliegue. Marcad sus trabajos como checks obligatorios.
  2. (20′) En una rama, fijad una versión antigua y vulnerable (por ejemplo flask==2.2.2 o requests==2.25.0) y abrid el PR. Observad qué herramientas lo bloquean y qué PR propone Dependabot.
  3. (15′) Romped a propósito la integración (cambiad el puerto en el Dockerfile) y comprobad que la prueba de integración falla antes de publicar nada.
  4. (25′) Entrega: repasad la lista de comprobación de la pestaña Recursos y completad el README con un apartado "Cómo se valida un cambio" que enlace a ACCESOS.md, docs/validacion.md y docs/seguridad.md.

Evidencia de evaluación

app.py

from flask import Flask, jsonify

CITAS = [{"id": 1, "paciente": "Ana", "dia": "2027-01-15"}]

@app.route("/salud")
def salud():
    return jsonify(estado="ok", entorno=os.getenv("ENTORNO", "local"))

@app.route("/citas")
def citas():
    return jsonify(CITAS)

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=int(os.getenv("PORT", 8000)))

COPY app.py .
USER app
EXPOSE 8000
HEALTHCHECK CMD python -c "import urllib.request;urllib.request.urlopen('http://localhost:8000/salud')"
