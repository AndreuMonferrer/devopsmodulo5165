Unidad 4. Modelos de servicio en la nube

SaaS, PaaS, IaaS y serverless: qué gestiona el proveedor y qué gestionas tú en cada modelo, y cuándo conviene cada uno.

Software como servicio (SaaS)

CE 4a

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Identificar la estructura de un servicio SaaS y explicar su funcionamiento.
  • Analizar un SaaS real que usáis a diario.

Introducción del tema

La pila y los modelos

            On premise   IaaS        PaaS        FaaS        SaaS
Aplicación     tú         tú          tú         tu código   proveedor
Datos          tú         tú          tú          tú         tú (tus datos)
Runtime        tú         tú        proveedor   proveedor    proveedor
Sistema op.    tú         tú        proveedor   proveedor    proveedor
Virtualización tú      proveedor    proveedor   proveedor    proveedor
Hardware/red   tú      proveedor    proveedor   proveedor    proveedor

SaaS

El proveedor ofrece una aplicación completa lista para usar, normalmente desde el navegador o una app, con suscripción por usuario o por uso. El cliente solo configura, da de alta usuarios y gestiona sus datos.

Estructura típica: un frontal web y API públicas; una capa de aplicación multi-tenant (una misma instancia sirve a todos los clientes, cada uno identificado por su tenant); almacenamiento con los datos separados por cliente; servicios de identidad (SSO, SAML/OIDC); y todo ello desplegado a su vez sobre IaaS o PaaS del propio proveedor o de un tercero.

Funcionamiento: el proveedor actualiza continuamente (despliegue continuo), sin que el cliente instale nada; la configuración se hace por tenant; la integración con otros sistemas, por API y webhooks.

Ejemplos: GitHub, Microsoft 365, Google Workspace, Salesforce, Slack, Jira, y en educación, Aules (Moodle) si se ofrece como servicio.

Actividad

En parejas, analizad un SaaS que usemos en el curso (GitHub, Google Workspace, Microsoft 365, Trello, Slack):

  1. (20′) Estructura: qué partes veis (web, API, apps, integraciones), dónde se alojan (buscad su página de estado y sus subprocesadores o trust center).
  2. (20′) Funcionamiento: cómo se identifica el cliente (organización, tenant), qué configura el cliente, cada cuánto despliegan (buscad su changelog), cómo se integra por API. Probad una llamada: curl https://api.github.com/users/TU_USUARIO.
  3. (20′) Responsabilidad: qué pasa si borráis un repositorio por error o si el proveedor cae. ¿Quién es responsable de qué? Buscad su SLA.
  4. (15′) Esquema de la estructura en diagrams.net.
Puesta en común

Cada pareja presenta su esquema en 2 minutos. Buscamos lo común a todos los SaaS.

Evidencia de evaluación

Análisis y esquema de un SaaS (CE 4a).

Plataforma como servicio (PaaS)

CE 4b

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Identificar la estructura de un PaaS y explicar su funcionamiento.
  • Desplegar una aplicación en un PaaS sin gestionar servidores.

Introducción del tema

PaaS

El proveedor ofrece una plataforma para ejecutar tus aplicaciones: sistema operativo, runtime (Python, Java, Node, .NET), servidor de aplicaciones, balanceo, escalado y parches. Tú subes el código (o una imagen de contenedor) y la configuración.

Estructura: un servicio de construcción que detecta el lenguaje y empaqueta la app (buildpacks), un conjunto de instancias gestionadas detrás de un balanceador, servicios añadidos (base de datos gestionada, caché, colas), variables de entorno para la configuración y registros y métricas integrados.

Funcionamiento: git push o subida de un zip, construcción automática, despliegue con cambio gradual de versión, escalado por número de instancias o automático. La filosofía de las aplicaciones de doce factores (config en variables de entorno, procesos sin estado, logs por salida estándar) nació en Heroku, uno de los primeros PaaS.

Ejemplos: AWS Elastic Beanstalk, Azure App Service, Google App Engine, Heroku, Render, Railway.

Actividad

  1. (10′) Cread un repositorio hola-cita con la mini-aplicación (pestaña Recursos).
  2. (45′) Desplegadla en el PaaS de vuestro proveedor:
    • AWS Learner Lab: Elastic Beanstalk, plataforma Python, subiendo un zip con app.py, requirements.txt y un Procfile con web: gunicorn app:app.
    • Azure for Students: App Service plan F1 (gratuito), despliegue desde GitHub o con az webapp up --runtime PYTHON:3.12 --sku F1.
  3. (10′) Definid la variable de entorno ENTORNO=paas desde la consola y comprobad que la web cambia sin tocar el código.
  4. (10′) Localizad en la consola: registros, métricas, número de instancias y cómo escalar. Anotad qué no habéis tenido que hacer (instalar Python, nginx, parches...).
Puesta en común

¿Cuántos minutos desde el código hasta la URL pública? ¿Qué pasa si subimos una versión con un error?

Evidencia de evaluación

URL funcionando y registro del despliegue con la estructura identificada (CE 4b).

Notas para el docente

Alternativa si ninguna nube está disponible: Render o Railway con capa gratuita, desplegando desde GitHub. Eliminar los entornos al acabar para no gastar crédito.

Infraestructura como servicio (IaaS)

CE 4c

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Identificar la estructura de un IaaS y explicar su funcionamiento.
  • Desplegar la misma aplicación sobre una máquina virtual y comparar el esfuerzo.

Introducción del tema

IaaS

El proveedor ofrece recursos de infraestructura virtualizados: máquinas virtuales, redes, discos, balanceadores, IP públicas. Todo lo que va encima de la máquina (SO, parches, runtime, aplicación, seguridad del sistema) es responsabilidad del cliente. Es el modelo con más control y más trabajo, y el más cercano a tener servidores propios.

Estructura: servicio de cómputo (EC2, Azure VM), red virtual (VPC/VNet, subredes, grupos de seguridad), almacenamiento de bloque, imágenes, claves SSH y la API que lo gestiona todo.

Funcionamiento: se aprovisiona a demanda (consola, CLI, API o Terraform), se factura por segundos de uso y tamaño, y se escala añadiendo máquinas (horizontal) o cambiando el tamaño (vertical). Es lo que ya hicimos en la sesión 10; hoy desplegamos una aplicación completa encima.

Actividad

  1. (15′) Lanzad una VM Ubuntu pequeña con los puertos 22 y 80 abiertos.
  2. (40′) Desplegad a mano la mini-aplicación: sudo apt install python3-venv nginx, clonad el repositorio, cread el entorno virtual, instalad dependencias, cread un servicio systemd con gunicorn y configurad nginx como proxy inverso al puerto 8000. Documentad cada comando en el README.
  3. (10′) Cread ENTORNO=iaas en la unidad systemd y reiniciad.
  4. (10′) Tabla: tareas que habéis hecho vosotros hoy y que en PaaS hacía el proveedor. Terminad la VM.
Puesta en común

Comparamos tiempo y número de comandos frente al PaaS. ¿Cuándo compensa este esfuerzo?

Evidencia de evaluación

Arquitectura sin servidor (serverless)

CE 4d

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Identificar la estructura de un servicio serverless y explicar su funcionamiento.
  • Crear una función que responde a peticiones HTTP.

Introducción del tema

Serverless

"Sin servidor" no significa que no haya servidores, sino que no los ves ni los gestionas, no pagas por tenerlos encendidos y escalan a cero. Engloba dos ideas:

  • FaaS (Function as a Service): escribes funciones que se ejecutan en respuesta a eventos (una petición HTTP, un fichero subido, un mensaje en una cola, un cron). AWS Lambda, Azure Functions, Google Cloud Functions.
  • Servicios gestionados serverless: bases de datos, colas o almacenamiento que se consumen por petición (DynamoDB, S3, SQS).

Estructura: origen del evento (API Gateway, S3, cola) → disparador → función (código + runtime + configuración de memoria y tiempo máximo) → servicios gestionados. Funcionamiento: la plataforma arranca un entorno aislado al llegar un evento, ejecuta la función y lo reutiliza o lo destruye; se factura por número de invocaciones y milisegundos × memoria. Limitaciones: tiempo máximo por ejecución, arranque en frío (cold start), funciones sin estado y mayor dependencia del proveedor.

# AWS Lambda en Python
def lambda_handler(event, context):
    return {"statusCode": 200,
            "headers": {"Content-Type": "text/plain"},
            "body": "Hola, cita previa. Servido por Lambda"}

Actividad

  1. (30′) Cread la función:
    • AWS: Lambda, runtime Python 3.12, rol LabRole en el Learner Lab, activad Function URL sin autenticación y probadla en el navegador.
    • Azure: Function App en plan de consumo, función HTTP trigger en Python desde el portal.
  2. (15′) Modificad la función para devolver en JSON la hora actual y el parámetro ?nombre= que llegue en la URL.
  3. (15′) Medid el arranque en frío: esperad unos minutos, invocad con curl -w "%{time_total}\n" URL y repetid seguido. Consultad la duración facturada en los registros (CloudWatch o Application Insights).
  4. (15′) Calculad con la calculadora el coste de 1 millón de invocaciones de 200 ms con 128 MB y comparadlo con una VM encendida todo el mes.
Puesta en común

¿Qué parte de «Cita Previa Salud» haríais serverless? (recordatorios por SMS, generación de justificantes en PDF...).

Evidencia de evaluación

Comparativa de modelos de servicio. Prueba de la unidad

CE 4e

Inicio10′Introducción15′Actividad45′Prueba escrita50′

Qué vas a saber hacer al terminar

  • Situar los servicios de contenedores entre los modelos.

Introducción del tema

El alcance de cada modelo

La comparación útil no es "cuál es mejor", sino qué gestiona cada parte y qué necesidad cubre. Cuanto más arriba en la pila, menos control y menos trabajo; cuanto más abajo, más flexibilidad y más responsabilidad.

¿Dónde encajan los contenedores?

  • Contenedores en tu VM (Docker en EC2 o Proxmox): IaaS.
  • Kubernetes gestionado (EKS, AKS, GKE): el plano de control lo gestiona el proveedor; los nodos, a veces tú. Entre IaaS y PaaS.
  • Contenedores sin servidores (AWS Fargate, Azure Container Apps, Google Cloud Run): CaaS, muy cerca de PaaS y serverless: das una imagen y escalan incluso a cero.

Por eso el curso de especialización se centra en la imagen de contenedor: es la unidad de despliegue que funciona en todos los modelos.

Añadid una fila para CaaS. Terminad con una recomendación para cada componente de "Cita Previa Salud".

app.py

from flask import Flask
import os, socket
app = Flask(__name__)

@app.route("/")
def hola():
    return f"Hola, cita previa. Servido por {socket.gethostname()} en {os.getenv('ENTORNO', 'local')}"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=int(os.getenv("PORT", 8000)))
