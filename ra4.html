Software como servicio (SaaS)

CE 4a

Objetivos de la sesión

  • Situar los modelos de servicio en la pila tecnológica y relacionarlos con la responsabilidad del cliente y del proveedor.
  • Describir el software como servicio (SaaS): su estructura interna, su funcionamiento, su modelo de negocio y sus formas de integración.
  • Evaluar un servicio SaaS con criterios técnicos, de seguridad y de negocio.
  • Comparar en la práctica un SaaS (GitHub) con la misma herramienta autoalojada (Gitea) e integrarse con un SaaS mediante su API.

1. Los modelos de servicio

El NIST define tres modelos de servicio: SaaS, PaaS e IaaS. A ellos se ha añadido el serverless (a veces llamado FaaS, funciones como servicio). Se distinguen por qué capas de la pila gestiona el proveedor y cuáles el cliente:

CapaOn premiseIaaSPaaSServerless (FaaS)SaaS
Datos y usuariosClienteClienteClienteClienteCliente
AplicaciónClienteClienteClienteCliente (solo funciones)Proveedor
Entorno de ejecución y middlewareClienteClienteProveedorProveedorProveedor
Sistema operativoClienteClienteProveedorProveedorProveedor
VirtualizaciónClienteProveedorProveedorProveedorProveedor
Servidores, almacenamiento, redClienteProveedorProveedorProveedorProveedor

Una analogía muy usada es la de la pizza: on premise es hacerla en casa desde cero; IaaS es comprar la base y cocinarla en tu horno; PaaS es pedirla a domicilio y ponerla tú en la mesa; SaaS es ir a la pizzería. Cuanto más a la derecha de la tabla, menos trabajo y menos control.

Recorremos los modelos de arriba abajo, empezando por el que más conocéis sin saberlo: el SaaS.

2. Qué es el SaaS

En el software como servicio, el proveedor ofrece una aplicación completa, lista para usar, que se ejecuta en su infraestructura. El cliente accede a través del navegador, de una aplicación móvil o de una API, y no gestiona ni controla nada de la infraestructura, del sistema operativo ni de la propia aplicación, salvo algunos ajustes de configuración y, por supuesto, sus datos y sus usuarios (definición del NIST).

Ejemplos: Gmail y Google Workspace, Microsoft 365, Salesforce, Slack, Zoom, Dropbox, Canva, Moodle en su versión en la nube, Aules (desde el punto de vista del alumnado). Y muchas herramientas DevOps que usaremos en el curso: GitHub, SonarQube Cloud, Docker Hub, Jira.

3. Estructura de un SaaS

Aunque el cliente no lo vea, un SaaS moderno suele tener esta estructura:

        Navegador        App móvil        Integraciones (API, webhooks)
             │               │                     │
     ┌───────┴───────────────┴─────────────────────┴───────┐
     │  Capa de acceso: CDN, balanceo, WAF, autenticación   │
     │  (SSO con SAML/OIDC, doble factor)                    │
     ├──────────────────────────────────────────────────────┤
     │  Aplicación (normalmente microservicios en           │
     │  contenedores sobre PaaS o IaaS del propio proveedor) │
     │  + configuración por cliente (inquilino)              │
     ├──────────────────────────────────────────────────────┤
     │  Datos: bases de datos multiinquilino, almacenamiento │
     ├──────────────────────────────────────────────────────┤
     │  Infraestructura: nube pública o CPD del proveedor    │
     └──────────────────────────────────────────────────────┘
     Operación, monitorización, copias y actualizaciones: el proveedor

Multitenencia en el SaaS

Una única instancia de la aplicación sirve a muchos clientes (inquilinos) a la vez, y cada uno ve solo sus datos. La separación de datos se implementa de tres formas principales:

ModeloCómoVentajasInconvenientes
Base de datos compartida, esquema compartidoTodas las tablas tienen una columna tenant_idEl más barato y fácil de escalarUn error de programación puede mostrar datos de otro cliente
Base de datos compartida, esquema por inquilinoCada cliente tiene su propio esquemaMejor aislamientoMás difícil de mantener con miles de clientes
Base de datos por inquilinoCada cliente, su base de datosAislamiento máximo, se puede ubicar por regiónMás caro; se reserva para clientes grandes o planes empresariales

Funcionamiento

  • Actualizaciones continuas: el proveedor despliega mejoras y correcciones a todos los clientes a la vez, a menudo varias veces al día (DevOps en acción). El cliente siempre usa la última versión, sin instalar nada, pero tampoco puede quedarse en una versión antigua.
  • Configuración, no programación: el cliente adapta el SaaS con opciones, campos personalizados, flujos y extensiones del marketplace, pero no modifica su código.
  • Identidad: los SaaS empresariales se integran con el directorio de la organización mediante inicio de sesión único (SSO) con SAML u OpenID Connect, y con SCIM para dar de alta y de baja usuarios automáticamente.
  • Integración: mediante API REST o GraphQL (el cliente consulta o modifica datos desde sus programas) y webhooks (el SaaS avisa a otra aplicación con una petición HTTP cuando ocurre algo, por ejemplo "se ha fusionado un pull request").

Modelo de negocio

  • Suscripción mensual o anual, normalmente por usuario (per seat) o por uso (número de mensajes, GB, ejecuciones).
  • Planes escalonados (gratuito, equipo, empresa) con más funciones, límites y soporte según el precio.
  • Freemium: plan gratuito limitado para captar usuarios. GitHub, por ejemplo, es gratuito para repositorios públicos y ofrece ventajas a estudiantes con GitHub Education.

4. Ventajas y riesgos del SaaS

VentajasRiesgos e inconvenientes
Disponible en minutos, sin instalaciónMenor control: funciones, cambios y calendario los decide el proveedor
Sin mantenimiento: parches, copias y escalado los hace el proveedorDependencia: salir puede ser difícil si no se pueden exportar los datos en un formato útil
Coste predecible por usuarioEl coste crece con el número de usuarios y puede superar al de una solución propia
Accesible desde cualquier lugar y dispositivoDepende de Internet y de la disponibilidad del proveedor
Siempre actualizadoUbicación y tratamiento de los datos (RGPD, ENS)
Seguridad profesionalTI en la sombra: cualquiera puede contratar un SaaS con una tarjeta

Responsabilidad del cliente en un SaaS

Aunque el proveedor lo gestiona casi todo, el cliente sigue siendo responsable de: quién tiene cuenta y con qué permisos, activar el doble factor, qué datos introduce y quién puede verlos, configurar correctamente la seguridad (por ejemplo, que un repositorio con secretos no sea público), revisar los registros de auditoría y tener una copia propia de los datos críticos. Muchos SaaS no garantizan recuperar datos borrados por error del cliente.

Criterios para evaluar un SaaS

Funcionalidad; seguridad (certificaciones, cifrado, doble factor, SSO, registros de auditoría); ubicación de los datos y contrato de encargado del tratamiento; SLA y soporte; precio y cómo crece; API e integraciones; exportación de datos y plan de salida; madurez y estabilidad del proveedor; accesibilidad e idioma.

5. SaaS frente a autoalojado

Muchas herramientas existen en las dos formas: como SaaS y como software que la organización instala en su infraestructura (self-hosted). GitHub.com frente a GitLab o Gitea autoalojados; Slack frente a Mattermost; Google Drive frente a Nextcloud; SonarQube Cloud frente a SonarQube Server. La decisión combina todo lo visto en las unidades 2 y 3: control y soberanía de los datos frente a esfuerzo de operación.

Plataforma como servicio (PaaS)

CE 4b

Objetivos de la sesión

  • Describir la plataforma como servicio (PaaS): su estructura y cómo funciona el despliegue de una aplicación.
  • Conocer los tipos de PaaS: de aplicaciones, de contenedores, de bases de datos y PaaS privado.
  • Relacionar el PaaS con los principios de las aplicaciones de doce factores.
  • Desplegar, configurar, escalar y actualizar cita-previa-app en un PaaS real.

1. Qué es el PaaS

En la plataforma como servicio, el proveedor ofrece un entorno listo para ejecutar aplicaciones que desarrolla el cliente. El cliente sube su código (o su imagen de contenedor) y la plataforma se encarga de todo lo demás: servidores, sistema operativo, entorno de ejecución (Python, Java, Node...), servidor web, balanceo, certificados HTTPS, escalado, registros y parches. Según el NIST, el cliente controla la aplicación desplegada y la configuración de su entorno, pero no la infraestructura subyacente.

La promesa del PaaS: que el equipo de desarrollo se ocupe solo del código. Heroku (2007) popularizó la idea con una frase: desplegar debería ser tan fácil como git push heroku main.

2. Estructura de un PaaS

Componentes

  • Entorno de ejecución (runtime): versiones soportadas de cada lenguaje. El proveedor las parchea, pero también las retira cuando quedan obsoletas, obligando a actualizar la aplicación.
  • Sistema de construcción: los buildpacks detectan el lenguaje por sus ficheros (requirements.txt → Python; package.json → Node) y preparan la aplicación sin necesidad de Dockerfile. Los PaaS modernos aceptan también imágenes de contenedor.
  • Definición de procesos: qué orden arranca la aplicación (por ejemplo, un Procfile con web: gunicorn app:app).
  • Configuración: variables de entorno y secretos gestionados por la plataforma, separados del código.
  • Enrutamiento y dominios: cada aplicación recibe una URL y se le pueden asociar dominios propios con certificado automático.
  • Escalado: número de instancias y tamaño de cada una, con reglas de autoescalado.
  • Servicios gestionados conectables: bases de datos (DBaaS), cachés, almacenamiento.
  • Observabilidad: registros agregados, métricas, estado de salud.
  • Despliegues: historial de versiones, vuelta atrás con un clic, a veces entornos de previsualización por cada pull request.

3. Tipos de PaaS

TipoQué ofreceEjemplos
PaaS de aplicacionesSe sube código y la plataforma lo ejecutaAWS Elastic Beanstalk, Azure App Service, Google App Engine, Heroku, Render
PaaS de contenedores (CaaS)Se sube una imagen de contenedor; la plataforma la ejecuta y escalaGoogle Cloud Run, Azure Container Apps, AWS ECS con Fargate, Fly.io
Bases de datos como servicio (DBaaS)Bases de datos gestionadasAmazon RDS, Azure SQL, Cloud SQL, MongoDB Atlas, Supabase

4. El PaaS y las aplicaciones de doce factores

Los ingenieros de Heroku resumieron en The Twelve-Factor App (12factor.net) las características que debe tener una aplicación para funcionar bien en un PaaS y, en general, en la nube. Varios de estos factores explican cómo funciona el PaaS:

FactorQué dicePor qué lo necesita el PaaS
I. Código baseUn repositorio por aplicación, muchos desplieguesRevisión y producción se despliegan desde el mismo código
II. DependenciasDeclaradas explícitamente (requirements.txt)El buildpack las instala sin intervención humana
III. ConfiguraciónEn variables de entorno, no en el códigoLa misma versión funciona en cada entorno
IV. Servicios de apoyoBases de datos, colas... como recursos conectables por URLSe cambia la base de datos cambiando una variable
V. Construir, publicar, ejecutarTres etapas separadasPermite volver a una publicación anterior
VI. ProcesosSin estado; lo persistente, en servicios de apoyoLas instancias se crean y destruyen continuamente; el disco local es efímero
VII. Asignación de puertosLa aplicación escucha en el puerto que le indican (PORT)El enrutador de la plataforma decide el puerto
VIII. ConcurrenciaSe escala añadiendo procesosEscalado horizontal
IX. DesechabilidadArranque rápido y parada limpiaDespliegues y escalados sin cortes
X. ParidadDesarrollo y producción lo más parecidos posibleEvitar el "en mi máquina funciona"
XI. RegistrosComo flujo de eventos por la salida estándarLa plataforma los recoge y centraliza
XII. AdministraciónTareas puntuales como procesos de una sola vezMigraciones de base de datos con la misma versión

Fijaos en que cita-previa-app ya cumple varios: lee PORT y ENTORNO de variables de entorno, declara sus dependencias y no guarda nada en disco.

5. Ventajas y limitaciones

VentajasLimitaciones
El equipo se centra en el código; mucho menos trabajo de sistemasSolo lenguajes y versiones soportados; restricciones (sin acceso root, disco efímero, tiempo máximo de petición)
Despliegue muy rápido y repetibleMenos control sobre el sistema y la red
Escalado, HTTPS, parches y balanceo incluidosDependencia del proveedor: configuraciones y servicios propios de cada plataforma
Historial de versiones y vuelta atrás sencillaCoste por instancia mayor que el de una VM equivalente
Entornos de revisión fáciles de crearDepuración más difícil (no se entra al servidor)

Cuándo elegir PaaS: aplicaciones web y API estándar, equipos pequeños sin personal de sistemas, prototipos y productos que deben salir rápido. Cuándo no: software que necesita control del sistema operativo, hardware especial, protocolos no HTTP o requisitos de red muy concretos.

Infraestructura como servicio (IaaS)

CE 4c

Objetivos de la sesión

  • Describir la infraestructura como servicio (IaaS): estructura, servicios que la forman y funcionamiento.
  • Identificar todas las tareas que asume el cliente en IaaS y compararlas con PaaS.
  • Conocer las operaciones habituales en IaaS: escalado vertical y horizontal, imágenes, instantáneas, grupos de autoescalado.
  • Desplegar a mano cita-previa-app en una VM de IaaS, dejarla como servicio del sistema y mantenerla.

1. Qué es el IaaS

En la infraestructura como servicio, el proveedor ofrece los recursos de computación fundamentales: capacidad de proceso, almacenamiento, redes y otros recursos, sobre los que el cliente puede desplegar y ejecutar cualquier software, incluidos sistemas operativos y aplicaciones. El cliente no gestiona la infraestructura física ni la virtualización, pero controla el sistema operativo, el almacenamiento y las aplicaciones, y tiene un control limitado de algunos componentes de red, como los cortafuegos (definición del NIST).

Es el modelo que más se parece a tener servidores propios, pero sin comprar hardware: por eso es el camino habitual para migrar aplicaciones existentes a la nube (lift and shift). En las sesiones 7, 10 y 11 ya habéis usado IaaS: las instancias EC2, las VPC, los volúmenes EBS y los buckets S3 son servicios IaaS.

2. Estructura del IaaS

En IaaS, el cliente ensambla estos bloques para construir su arquitectura (sesión 9): decide cuántas máquinas, de qué tamaño, en qué subredes, con qué discos y con qué reglas de red.

3. Qué hace el cliente en IaaS

Todo lo que el PaaS nos daba hecho, en IaaS lo hacemos nosotros:

  1. Diseñar la red: VPC, subredes, rutas, grupos de seguridad.
  2. Elegir y crear la máquina: tamaño, imagen, disco, claves.
  3. Administrar el sistema operativo: usuarios, SSH, parches de seguridad, cortafuegos interno, sincronización horaria, registros.
  4. Instalar el entorno de ejecución: Python y sus librerías, o Docker.
  5. Desplegar la aplicación y hacer que arranque sola como servicio (systemd) y se reinicie si falla.
  6. Poner un servidor web delante (nginx) como proxy inverso, con HTTPS (certificados con Let's Encrypt y su renovación).
  7. Escalar: añadir máquinas, balanceador, autoescalado.
  8. Monitorizar: instalar agentes, definir alarmas.
  9. Copias de seguridad: instantáneas de discos, copias de datos.
  10. Actualizar la aplicación y el sistema sin cortar el servicio.

A cambio, tenemos control total del sistema: cualquier lenguaje, cualquier versión, cualquier software, cualquier puerto o protocolo, acceso root. Es el modelo más flexible y el que más trabajo exige. Por eso en IaaS es imprescindible la automatización: infraestructura como código para crear los recursos (Terraform, unidad 6) y gestión de configuración para el software (Ansible, unidad 7). Sin ella, cada máquina acaba siendo un "copo de nieve": única, configurada a mano e imposible de reproducir.

4. Operaciones habituales

Escalado vertical

Cambiar el tipo de instancia a uno mayor o menor. Requiere detener la máquina (en la mayoría de proveedores) y arrancarla de nuevo. Útil cuando la aplicación no puede repartirse entre varias máquinas.

Escalado horizontal y autoescalado

Un grupo de autoescalado mantiene un número de instancias idénticas creadas a partir de una plantilla de lanzamiento (imagen, tipo, red, datos de usuario). Se define un mínimo, un máximo y una capacidad deseada, y unas políticas: "si la CPU media supera el 70 % durante 5 minutos, añade una instancia". Si una instancia falla su comprobación de salud, el grupo la sustituye automáticamente. Delante, un balanceador reparte el tráfico.

Imágenes e instantáneas

  • Instantánea (snapshot): copia de un disco en un momento dado. Para copias de seguridad o para clonar discos.
  • Imagen propia: plantilla creada a partir de una máquina configurada, para lanzar otras iguales rápidamente (imagen de oro). Se puede automatizar su construcción con Packer.

Infraestructura mutable e inmutable

  • Mutable: las máquinas se crean una vez y se van modificando (parches, nuevas versiones) durante años. Con el tiempo cada una diverge de las demás (configuration drift).
  • Inmutable: nunca se modifica una máquina en funcionamiento; para cambiar algo se crea una imagen nueva y se sustituyen las máquinas. Es la filosofía de los contenedores y de los grupos de autoescalado.

5. Cuándo elegir IaaS

  • Migrar aplicaciones existentes sin reescribirlas.
  • Software que necesita control del sistema operativo, versiones concretas, módulos del kernel o licencias ligadas a la máquina.
  • Protocolos o puertos que un PaaS no admite.
  • Montar plataformas propias encima: un clúster Kubernetes, una base de datos con configuración especial, un servidor de CI.
  • Entornos de pruebas que deben parecerse a los servidores on premise.

Su principal inconveniente es la carga de operación: con IaaS, el cliente sigue siendo responsable de más de la mitad de la pila (tabla de la sesión 18).

Arquitectura sin servidor (serverless)

CE 4d

Objetivos de la sesión

  • Describir la arquitectura sin servidor (serverless): funciones como servicio (FaaS) y servicios gestionados (BaaS).
  • Identificar su estructura: eventos, disparadores, funciones, entorno de ejecución y servicios asociados.
  • Explicar su funcionamiento: escalado automático hasta cero, arranque en frío, límites y facturación por invocación.
  • Crear funciones serverless que respondan a peticiones HTTP y a eventos, y calcular su coste.

1. Qué es serverless

"Sin servidor" no significa que no haya servidores: significa que el cliente no ve ni gestiona ningún servidor, ni siquiera el tamaño o el número de instancias. Escribe su código en forma de funciones que se ejecutan cuando ocurre un evento, y el proveedor se encarga de todo lo demás: aprovisionar la capacidad, escalar de cero a miles de ejecuciones simultáneas y volver a cero, aplicar parches y garantizar la disponibilidad.

Se consideran serverless los servicios que cumplen estas características:

  • Sin gestión de servidores ni de capacidad.
  • Escalado automático, incluido el escalado hasta cero cuando no hay actividad.
  • Pago por uso real: por ejecución y por tiempo de ejecución, no por tener algo encendido. Si nadie usa la aplicación, el coste es cero (o casi).
  • Alta disponibilidad integrada.

El serverless tiene dos componentes:

  • FaaS (Functions as a Service): el código propio en forma de funciones. AWS Lambda (2014, el primero de los grandes), Azure Functions, Google Cloud Run functions, Cloudflare Workers.
  • BaaS (Backend as a Service): servicios gestionados que la función usa y que también escalan y se pagan por uso: bases de datos (DynamoDB, Firestore), almacenamiento de objetos (S3), autenticación (Cognito, Firebase Auth), colas (SQS), API (API Gateway).

Hoy el término se aplica también a otros servicios con las mismas características, como los contenedores serverless (Google Cloud Run, AWS Fargate, Azure Container Apps) o las bases de datos serverless (Aurora Serverless).

2. Estructura

Elementos

  • Función: un fragmento de código con un punto de entrada (handler) que recibe el evento y un contexto, y devuelve un resultado. Debe ser sin estado: nada se conserva de una ejecución a otra salvo lo que se guarde en un servicio externo.
  • Disparador (trigger): lo que provoca la ejecución: una petición HTTP (a través de un API Gateway o de una URL de función), la subida de un fichero, un mensaje en una cola, un evento programado, un cambio en una base de datos...
  • Entorno de ejecución: el lenguaje y su versión (Python, Node, Java, Go, .NET) o una imagen de contenedor.
  • Configuración: memoria asignada (de la que suele depender también la CPU), tiempo máximo de ejecución, variables de entorno, concurrencia máxima.
  • Permisos: un rol que define a qué servicios puede acceder la función (mínimo privilegio).

3. Funcionamiento

Ciclo de una invocación

  1. Llega un evento.
  2. Si no hay ningún entorno de ejecución disponible, la plataforma crea uno: descarga el código, arranca un microentorno aislado (AWS usa microVM Firecracker), inicia el entorno del lenguaje y ejecuta el código de inicialización. Es el arranque en frío (cold start), que puede tardar desde decenas de milisegundos hasta varios segundos.
  3. Ejecuta el handler con el evento.
  4. Devuelve el resultado.
  5. El entorno se mantiene un tiempo "caliente" para reutilizarlo en las siguientes invocaciones (arranque en caliente, mucho más rápido). Si no se usa, se destruye.

Si llegan 100 eventos a la vez, la plataforma crea hasta 100 entornos en paralelo: el escalado es automático y casi instantáneo, dentro de los límites de concurrencia de la cuenta.

Límites típicos

Los números concretos cambian con el tiempo y conviene consultarlos en la documentación, pero como referencia, en AWS Lambda: tiempo máximo de ejecución de 15 minutos, memoria de 128 MB a 10 GB, tamaño del paquete limitado y un límite de ejecuciones concurrentes por cuenta y región. Por eso el serverless sirve para tareas cortas, no para procesos que corren durante horas.

Facturación

Se paga por número de invocaciones y por tiempo de ejecución multiplicado por la memoria asignada (GB-segundo), más los servicios BaaS que se usen. Hay capa gratuita generosa: AWS Lambda incluye cada mes un millón de invocaciones y 400.000 GB-s gratis.

Ejemplo: una función de 512 MB que tarda 200 ms, invocada 3 millones de veces al mes, consume 3.000.000 × 0,2 s × 0,5 GB = 300.000 GB-s. Con los precios de lista aproximados de Lambda (en torno a 0,0000167 $ por GB-s y 0,20 $ por millón de invocaciones), y sin capa gratuita, serían unos 5 $ de ejecución + 0,60 $ de invocaciones al mes. Con capa gratuita, prácticamente nada. Una VM encendida todo el mes para lo mismo costaría más, pero con tráfico alto y constante la VM acaba siendo más barata.

3. Otros servicios "como servicio"

El sufijo "como servicio" se ha aplicado a casi todo (XaaS, anything as a service). Algunos habituales:

  • DBaaS: bases de datos como servicio (RDS, Cloud SQL, MongoDB Atlas).
  • STaaS: almacenamiento como servicio.
  • DaaS: escritorio como servicio (Amazon WorkSpaces, Windows 365).
  • BaaS: backend como servicio (Firebase, Supabase) o copia de seguridad como servicio.
  • DRaaS: recuperación ante desastres como servicio.
  • SECaaS: seguridad como servicio (WAF, antivirus, SIEM gestionados).
  • AIaaS / MLaaS: inteligencia artificial como servicio (modelos a través de API).

4. Cómo elegir el modelo de servicio

Para cada componente de una aplicación, recorred estas preguntas en orden:

  1. ¿Existe ya un SaaS que resuelva la necesidad y cumpla los requisitos de seguridad y datos? (correo, gestión de proyectos, videollamadas, envío de SMS). Si es así, normalmente es lo más eficiente: no se desarrolla lo que se puede contratar.
  2. ¿Es una tarea corta, disparada por eventos, con tráfico irregular? → serverless.
  3. ¿Es una aplicación web o API estándar en un lenguaje soportado, sin necesidades especiales de sistema? → PaaS o contenedores serverless/gestionados.
  4. ¿Necesita control del sistema, software especial, protocolos no HTTP, licencias ligadas a la máquina o es una aplicación heredada? → IaaS (idealmente automatizado con IaC y gestión de configuración, y con contenedores dentro).
  5. Revisad después costes a la escala prevista, conocimientos del equipo, dependencia del proveedor y requisitos normativos.

import os, socket
app = Flask(__name__)

@app.route("/")
def hola():
    return f"Hola, cita previa. Servido por {socket.gethostname()} en {os.getenv('ENTORNO', 'local')}"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=int(os.getenv("PORT", 8000)))
