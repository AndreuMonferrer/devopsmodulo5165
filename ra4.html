    1. Quién gestiona cada capa

    El NIST define tres modelos de servicio: SaaS, PaaS e IaaS. A ellos se ha añadido el serverless (a veces llamado FaaS, funciones como servicio). Todos se distinguen con una sola pregunta: qué capas de la pila gestiona el proveedor y cuáles el cliente.

    CapaOn premiseIaaSPaaSServerless (FaaS)SaaS
    Datos y usuariosClienteClienteClienteClienteCliente
    AplicaciónClienteClienteClienteCliente (solo funciones)Proveedor
    Entorno de ejecución y middlewareClienteClienteProveedorProveedorProveedor
    Sistema operativoClienteClienteProveedorProveedorProveedor
    VirtualizaciónClienteProveedorProveedorProveedorProveedor
    Servidores, almacenamiento, redClienteProveedorProveedorProveedorProveedor

    Una analogía muy usada es la de la pizza: on premise es hacerla en casa desde cero. IaaS es comprar la base y cocinarla en tu horno. PaaS es pedirla a domicilio y ponerla tú en la mesa. SaaS es ir a la pizzería. Cuanto más a la derecha de la tabla, menos trabajo y menos control.

    Las capas que gestiona el cliente son también las que tiene que asegurar. Es el modelo de responsabilidad compartida: en IaaS los parches del sistema operativo son cosa del cliente, en PaaS y serverless los aplica el proveedor, y en SaaS el cliente solo responde de sus datos, sus usuarios y su configuración.

    2. IaaS: infraestructura como servicio

    El proveedor ofrece máquinas virtuales, discos y redes, y el cliente monta encima todo lo demás. Es lo más parecido a tener servidores propios, pero sin comprar hardware ni gestionar el CPD.

    • Estructura: cómputo (máquinas virtuales de distintas familias y tamaños), almacenamiento (de bloque, de objetos, de ficheros) y red (redes virtuales, subredes, grupos de seguridad, balanceadores). Son los componentes que vimos en la unidad 2.
    • Funcionamiento: el cliente lanza una máquina a partir de una imagen, elige su tamaño y su red, entra por SSH y a partir de ahí la administra: instala el software, aplica parches, configura el cortafuegos, hace copias. Para crecer puede cambiar a una máquina más grande (escalado vertical) o añadir más máquinas detrás de un balanceador (escalado horizontal).
    • Se paga por el tiempo que los recursos están encendidos o reservados.
    • Claves técnicas: la alta disponibilidad la diseña el cliente (varias máquinas en varias zonas de disponibilidad, detrás de un balanceador). El autoescalado se basa en una plantilla de lanzamiento y en comprobaciones de salud que sustituyen las máquinas que fallan. En lugar de parchear máquinas en marcha (infraestructura mutable), lo habitual es preparar una imagen nueva y sustituirlas (infraestructura inmutable), lo que evita que cada servidor acabe siendo distinto.
    • Ejemplos: Amazon EC2, Azure Virtual Machines, Google Compute Engine.

    3. PaaS: plataforma como servicio

    El proveedor ofrece una plataforma lista para ejecutar aplicaciones. El cliente aporta el código (o una imagen de contenedor) y la configuración, y no ve ni administra las máquinas ni el sistema operativo.

    • Estructura: entornos de ejecución para varios lenguajes (Python, Java, Node.js…), un proceso que construye la aplicación a partir del código, un balanceador que reparte el tráfico, escalado automático, registros y métricas, y servicios añadidos como bases de datos o colas.
    • Funcionamiento: el desarrollador sube el código (por ejemplo, con un git push), la plataforma lo construye, lo despliega en sus servidores y le da una URL. Las variables de entorno sirven para la configuración, y la plataforma permite volver a la versión anterior si algo falla.
    • Se paga por las instancias que ejecutan la aplicación y el tiempo que están en marcha.
    • Claves técnicas: la plataforma puede parar, mover o multiplicar las instancias en cualquier momento, así que la aplicación tiene que ser sin estado. Los ficheros y las sesiones van a servicios externos (almacenamiento de objetos, base de datos, caché), nunca al disco de la instancia. Es lo que recoge la metodología twelve-factor: configuración en variables de entorno, registros por la salida estándar y procesos que se pueden arrancar y parar sin perder nada. A cambio, el cliente renuncia al acceso de administrador y queda limitado a los lenguajes y versiones que soporta la plataforma.
    • Ejemplos: AWS Elastic Beanstalk, Azure App Service, Google App Engine, Heroku. Una base de datos gestionada como Amazon RDS sigue la misma idea aplicada a una base de datos.

    4. Serverless: funciones como servicio

    El cliente solo escribe funciones, fragmentos de código que se ejecutan cuando ocurre un evento. No hay servidores que dimensionar: el proveedor arranca las instancias necesarias y las para cuando no hay trabajo.

    • Estructura: la función (el código y su configuración de memoria y tiempo máximo), el disparador que la activa (una petición HTTP, la subida de un fichero, un mensaje en una cola, una hora programada) y los servicios gestionados con los que trabaja (almacenamiento, bases de datos, colas).
    • Funcionamiento: llega el evento, el proveedor busca una instancia libre o arranca una nueva, ejecuta la función y devuelve el resultado. La primera ejecución tras un rato sin uso tarda algo más (arranque en frío). Las funciones no guardan estado entre ejecuciones y tienen límites de duración (en AWS Lambda, 15 minutos como máximo), así que encajan en tareas cortas.
    • Se paga por ejecución y por el tiempo de cómputo consumido. Si no hay eventos, el coste es prácticamente cero.
    • Claves técnicas: cada instancia atiende una petición a la vez, y hay un límite de ejecuciones simultáneas por cuenta. El arranque en frío se puede reducir manteniendo instancias preparadas (concurrencia aprovisionada), aunque eso se paga aparte. Muchos disparadores entregan los eventos al menos una vez, así que un mismo evento puede llegar repetido y la función tiene que ser idempotente: ejecutarla dos veces debe dar el mismo resultado que una. Con tráfico alto y constante, el pago por ejecución puede salir más caro que una máquina o un contenedor encendidos todo el día.
    • Ejemplos: AWS Lambda, Azure Functions, Google Cloud Run functions.

    5. SaaS: software como servicio

    El proveedor ofrece una aplicación completa, lista para usar, que se ejecuta en su infraestructura. El cliente accede por el navegador, una aplicación móvil o una API, y solo gestiona sus datos, sus usuarios y algunos ajustes.

    • Estructura: una aplicación multitenencia, en la que una sola instancia atiende a muchos clientes con sus datos separados, una capa de acceso con autenticación (a menudo con inicio de sesión único, SSO) y una API para integrarla con otros sistemas.
    • Funcionamiento: el cliente se da de alta, configura usuarios y permisos y empieza a usarla. El proveedor actualiza la aplicación para todos a la vez, sin que el cliente tenga que hacer nada.
    • Se paga con una suscripción, normalmente por usuario y mes o por uso.
    • Claves técnicas: la multitenencia admite varios diseños, desde una base de datos compartida en la que cada fila lleva el identificador del cliente hasta una instancia separada por cliente, más cara pero más aislada. En las empresas, los usuarios se gestionan desde su propio directorio con SSO (SAML u OpenID Connect) y se dan de alta y de baja automáticamente con SCIM. Antes de contratar conviene revisar el SLA, dónde se guardan los datos (por el RGPD) y cómo se exportan si un día se cambia de proveedor.
    • Ejemplos: Google Workspace, Microsoft 365, Salesforce, Slack. Y muchas herramientas DevOps del curso: GitHub, Docker Hub, SonarQube Cloud.

    Actividades

    Actividad 1. La misma web, tres modelos

    Para qué: comprobar con vuestro propio portátil qué tenéis que hacer vosotros y qué hace el proveedor en IaaS, PaaS y serverless, publicando la misma página de las tres formas.

    Individual. Antes de empezar necesitáis:

    • Docker instalado en el portátil. Si un comando de Docker da error de permisos, ponedle sudo delante.
    • Una cuenta de GitHub.
    • Firefox.

    Preparación. Cread en vuestra carpeta personal un archivo index.html con este contenido, cambiando el nombre por el vuestro:

    <!DOCTYPE html>
<html>
  <head><meta charset="utf-8"><title>Mi web</title></head>
  <body>
    <h1>Web de Nombre Apellido</h1>
    <p>Esta página se publica con tres modelos de servicio distintos.</p>
  </body>
</html>

    Parte A. IaaS: lo gestionáis todo vosotros

    En IaaS el proveedor os da una máquina con el sistema operativo instalado y todo lo demás es cosa vuestra. Lo simuláis con un contenedor Ubuntu vacío en el portátil. No es una nube, pero el trabajo que hacéis es el mismo que en una máquina virtual de Amazon EC2.

    1. Arrancad un contenedor Ubuntu que redirige el puerto 8080 del portátil al puerto 80 del contenedor: 
      docker run -it --name iaas -p 8080:80 ubuntu bash
    2. Dentro del contenedor, instalad el servidor web nginx: 
      apt update
apt install -y nginx
      Si os pregunta la zona horaria, elegid Europe y después Madrid.
    3. Abrid otra terminal en el portátil y copiad vuestra página dentro del contenedor: 
      docker cp ~/index.html iaas:/var/www/html/index.html
    4. Volved a la terminal del contenedor y arrancad nginx: 
      nginx
    5. Abrid http://localhost:8080 en Firefox y comprobad que aparece vuestra página.

    Parte B. PaaS: subís la página y la plataforma la sirve

    GitHub Pages solo publica páginas estáticas, así que es un PaaS muy sencillo. Aun así, la idea es la misma que en AWS Elastic Beanstalk o Azure App Service: vosotros aportáis el contenido y la plataforma se encarga de servirlo.

    1. En GitHub, cread un repositorio público llamado web-paas.
    2. Pulsad Add file → Upload files, subid vuestro index.html y confirmad con Commit changes.
    3. Id a Settings → Pages. En Source elegid Deploy from a branch, la rama main y la carpeta / (root), y guardad.
    4. Esperad un par de minutos y abrid https://vuestro-usuario.github.io/web-paas/

    Parte C. Serverless: solo escribís la función

    En serverless no hay servidor que instalar ni que arrancar: escribís una función que se ejecuta cada vez que llega una petición y devuelve la respuesta. Usaréis el Playground de Cloudflare Workers, que funciona en el navegador y no necesita cuenta.

    1. Abrid https://workers.cloudflare.com/playground en Firefox.
    2. En el archivo principal (index.js), borrad todo el código y pegad este. Entre las comillas invertidas va el contenido de vuestro index.html: 
      export default {
  fetch(request) {
    const html = `aquí va el contenido de vuestro index.html`
    return new Response(html, {
      headers: { "content-type": "text/html" }
    })
  }
}
    3. Comprobad en la vista previa de la derecha que aparece vuestra página.
    4. Pulsad Copy Link para obtener el enlace de lo que habéis hecho.

    Parte D. Publicar un cambio

    Cambiad el título por Web de Nombre Apellido · versión 2 y volved a publicarlo con los tres modelos:

    • IaaS: editad index.html en el portátil, repetid el docker cp del paso 3 y recargad localhost:8080.
    • PaaS: en el repositorio web-paas, abrid index.html, pulsad el lápiz para editarlo, cambiad el título y confirmad con Commit changes. Esperad un poco y recargad la página.
    • Serverless: cambiad el título dentro de la función y mirad la vista previa.

    Cuando acabéis, podéis parar el contenedor con docker stop iaas.

    La idea que resume la tabla: cuanto más arriba en la pila se sitúa el servicio, más rápido se empieza y menos se opera, pero menos se controla y más se depende del proveedor. No hay un modelo mejor que otro, sino un modelo adecuado para cada necesidad.

    2. ¿Y los contenedores?

    Los servicios de contenedores no encajan limpiamente en la clasificación del NIST, que es de 2011, y por eso se habla de CaaS (Containers as a Service). Según cuánto gestione el proveedor, se acercan a un modelo u otro:

    ServicioQué gestiona el clienteSe acerca a
    Docker en una VM (lo que haremos en la unidad 7)La VM, el SO, Docker y los contenedoresIaaS
    Kubernetes gestionado (EKS, AKS, GKE)Los nodos (en parte), los objetos de Kubernetes y los contenedores. El proveedor gestiona el plano de controlEntre IaaS y PaaS
    Orquestador del proveedor con servidores gestionados (ECS con Fargate)Definiciones de tareas y serviciosPaaS
    Contenedores serverless (Cloud Run, Azure Container Apps)Solo la imagen y la configuración. Escala a cero y se paga por usoServerless

    La gran ventaja de los contenedores es que la misma imagen puede ir por cualquiera de estos niveles, así que el modelo de servicio se puede cambiar sin rehacer la aplicación.

    3. Cómo elegir el modelo de servicio

    Para cada componente de un sistema, estas preguntas en orden ayudan a decidir:

    1. ¿Existe ya un SaaS que resuelva la necesidad y cumpla los requisitos de seguridad y de datos? Si es así, suele ser lo más eficiente: no se desarrolla lo que se puede contratar.
    2. ¿Es una tarea corta, disparada por eventos o con tráfico irregular? → serverless.
    3. ¿Es una aplicación web o una API estándar en un lenguaje soportado? → PaaS o contenedores gestionados.
    4. ¿Necesita control del sistema operativo, software especial o es una aplicación heredada? → IaaS.
    5. Después conviene revisar el coste a la escala prevista, lo que sabe hacer el equipo, la dependencia del proveedor y los requisitos legales.

    Las arquitecturas reales combinan modelos. Por ejemplo, un sistema de cita previa de un centro de salud podría quedar así:

    ComponenteModeloPor qué
    Correo y ofimática del personalSaaSNecesidad estándar, no hay nada que desarrollar
    Web y API de citasPaaS o contenedores gestionadosAplicación propia con tráfico continuo y picos
    Base de datos de citasBase de datos gestionadaCopias y réplicas a cargo del proveedor
    Recordatorios diarios por SMSServerless programadoTarea corta una vez al día
    Integración con un programa antiguo de historia clínicaIaaSSoftware heredado con requisitos especiales
