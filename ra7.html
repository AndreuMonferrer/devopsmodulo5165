Ansible: instalar herramientas y dependencias en la infraestructura

CE 7a

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Instalar Ansible en el nodo de control y conectar con la infraestructura.
  • Instalar con un playbook Docker y las dependencias de la aplicación, gestionando también las dependencias de Ansible.

Introducción del tema

Gestión de la configuración

Terraform crea recursos; Ansible configura lo que hay dentro. Funciona sin agente (se conecta por SSH), es declarativo en sus módulos (dices "el paquete debe estar instalado", no "instálalo") e idempotente: repetir no cambia lo que ya está bien.

Gestores de paquetes y dependencias

En la infraestructura conviven varios niveles: paquetes del sistema (apt), dependencias de lenguaje (pip, npm), imágenes de contenedor (docker pull) y las propias dependencias de Ansible: las colecciones, que se declaran en requirements.yml y se instalan con ansible-galaxy.

[revision:children]

ansible/instalar.yml

- name: Instalar Docker Engine y dependencias
  hosts: web
  become: true
  tasks:
    - name: Paquetes base y SDK de Docker para Python
      ansible.builtin.apt:
        name: [ca-certificates, curl, python3-docker, jq]
        update_cache: true
    - name: Clave del repositorio oficial de Docker
      ansible.builtin.get_url:
        url: https://download.docker.com/linux/ubuntu/gpg
        dest: /etc/apt/keyrings/docker.asc
        mode: "0644"
    - name: Repositorio oficial de Docker
      ansible.builtin.apt_repository:
        repo: "deb [signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu {{ ansible_distribution_release }} stable"
        filename: docker
    - name: Docker Engine y plugin Compose
      ansible.builtin.apt:
        name: [docker-ce, docker-ce-cli, containerd.io, docker-compose-plugin]
        update_cache: true
    - name: Servicio Docker activo al arrancar
      ansible.builtin.service:
        name: docker
        state: started
        enabled: true
    - name: El usuario de despliegue puede usar Docker
      ansible.builtin.user:
        name: despliegue
        groups: docker
        append: true

Flujos de mantenimiento y despliegue con roles

CE 7b

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Organizar la automatización en roles reutilizables.
  • Crear flujos de mantenimiento de la configuración y de despliegue de la aplicación.

Introducción del tema

De playbooks sueltos a roles

Un rol agrupa tareas, plantillas, handlers y valores por defecto de una responsabilidad concreta. Se crea con ansible-galaxy role init roles/base:

roles/base/
├── defaults/main.yml   # valores por defecto (se pueden sobrescribir)
├── tasks/main.yml      # tareas
├── handlers/main.yml   # acciones que se disparan con notify
└── templates/          # plantillas Jinja2 (.j2)

Qué es mantenimiento

Tareas que se repiten para que los sistemas sigan sanos y homogéneos: actualizaciones de seguridad, usuarios y claves, hora, limpieza de disco, rotación de registros y configuración de servicios.

- name: Actualizar paquetes

    upgrade: safe
    update_cache: true
    cache_valid_time: 3600
- name: Actualizaciones de seguridad automáticas
  ansible.builtin.apt:
    name: unattended-upgrades
- name: Zona horaria
  community.general.timezone:
    name: Europe/Madrid
- name: Configuración de SSH endurecida
  ansible.builtin.template:
    src: sshd_extra.conf.j2
    dest: /etc/ssh/sshd_config.d/10-extra.conf
    mode: "0644"
  notify: Reiniciar ssh
- name: Limpieza semanal de imágenes de Docker sin usar

    name: docker-prune

    hour: "4"
    minute: "0"

Verificar que la automatización hace lo que debe

CE 7c

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Probar los flujos de mantenimiento en varios niveles antes y después de ejecutarlos.
  • Automatizar la verificación en un workflow.

Introducción del tema

Niveles de verificación

  1. Estática: --syntax-check y ansible-lint.
  2. Simulación: --check --diff muestra qué cambiaría sin tocar nada.
  3. Idempotencia: la segunda ejecución debe terminar con changed=0. Si no, alguna tarea no está bien escrita.
  4. Resultado: tareas que comprueban el estado final con assert, uri o command + changed_when: false.

verificar.yml

- name: Verificar mantenimiento y despliegue
  hosts: web
  become: true
  tasks:
    - name: Datos de servicios
      ansible.builtin.service_facts:
    - name: Docker y ssh activos
      ansible.builtin.assert:
        that:
          - ansible_facts.services['docker.service'].state == 'running'
          - ansible_facts.services['ssh.service'].state == 'running'
    - name: SSH no admite contraseñas
      ansible.builtin.command: sshd -T
      register: sshd
      changed_when: false
      failed_when: "'passwordauthentication no' not in sshd.stdout"
    - name: La aplicación responde
      ansible.builtin.uri:
        url: "http://localhost:{{ app_puerto }}/salud"
        return_content: true
      register: salud
      failed_when: salud.json.estado != 'ok'
    - name: Zona horaria correcta
      ansible.builtin.command: timedatectl show -p Timezone --value
      register: tz
      changed_when: false
      failed_when: tz.stdout != 'Europe/Madrid'

Actividad

  1. (15′) Pasad ansible-lint a todo el proyecto y corregid los avisos.
  2. (15′) Cambiad algo a mano en la VM (parad el contenedor, activad PasswordAuthentication yes) y ejecutad el mantenimiento con --check --diff: ¿lo detecta? Aplicad y comprobad que lo corrige.
  3. (15′) Prueba de idempotencia: ejecutad dos veces seguidas y guardad el resumen de la segunda. Corregid las tareas que sigan marcando changed.
  4. (15′) Escribid verificar.yml con al menos 5 comprobaciones (las del ejemplo más una vuestra) y ejecutadlo.
  5. (15′) Workflow ansible.yml: en PR, lint y --syntax-check en un runner de GitHub; en main, en el runner autohospedado, mantenimiento + despliegue + verificación en revisión.
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pipx install ansible-lint && cd ansible && ansible-lint
  aplicar:
    if: github.ref == 'refs/heads/main'
    needs: lint
    runs-on: [self-hosted, linux]
    environment: revision
    defaults: { run: { working-directory: ansible } }
    steps:
      - uses: actions/checkout@v4
      - run: ansible-galaxy collection install -r requirements.yml
      - run: ansible-playbook mantenimiento.yml desplegar.yml
      - run: ansible-playbook verificar.yml

Inicio10′Introducción20′Actividad75′Cierre15′

Introducción del tema

La pila

cAdvisor expone métricas de cada contenedor (CPU, memoria, red, disco); node-exporter, las del servidor; Prometheus las recoge cada pocos segundos y las guarda como series temporales; Grafana las dibuja en paneles.

roles/monitor/files/docker-compose.yml

services:
  prometheus:
    image: prom/prometheus:v3.5.0
    volumes: ["./prometheus.yml:/etc/prometheus/prometheus.yml:ro"]
    ports: ["9090:9090"]
  cadvisor:
    image: gcr.io/cadvisor/cadvisor:v0.52.1
    volumes:
      - /:/rootfs:ro
      - /var/run:/var/run:ro
      - /sys:/sys:ro
      - /var/lib/docker/:/var/lib/docker:ro
  node-exporter:
    image: prom/node-exporter:v1.9.1
    pid: host
    volumes: ["/:/host:ro,rslave"]
    command: ["--path.rootfs=/host"]
  grafana:
    image: grafana/grafana:12.1.0
    ports: ["3000:3000"]

roles/monitor/files/prometheus.yml

global:
  scrape_interval: 15s
scrape_configs:
  - job_name: contenedores
    static_configs: [{ targets: ["cadvisor:8080"] }]
  - job_name: servidor
    static_configs: [{ targets: ["node-exporter:9100"] }]

Del dato al capacity plan

Un capacity plan responde: ¿cuánto consumimos ahora, cuánto consumiremos si crece la demanda y cuándo hay que ampliar? Se mide el consumo con una carga conocida, se calcula el consumo por unidad (por ejemplo, MB por cada 100 peticiones por segundo) y se proyecta con el crecimiento previsto, dejando un margen (normalmente no superar el 70-80 %).

# Consultas PromQL útiles
rate(container_cpu_usage_seconds_total{name=~"cita-previa.*"}[1m])   # CPU por contenedor
container_memory_working_set_bytes{name=~"cita-previa.*"}            # memoria en uso
100 * (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)  # % memoria del servidor

        image: "{{ app_imagen }}:{{ app_version_anterior }}"
        state: started
        recreate: true

      ansible.builtin.uri:

        method: POST
        body: "Despliegue de {{ app_version }} en {{ entorno }} FALLIDO. Restaurada {{ app_version_anterior }}"

        msg: "Despliegue revertido"

ntfy.sh es un servicio de notificaciones por HTTP: suscribiéndoos a un canal con nombre difícil de adivinar desde su app o web recibís los avisos en el móvil. Es igual de fácil con un webhook de Slack, Discord, Teams o Telegram.

Salud de contenedores: Docker marca un contenedor como unhealthy si falla su healthcheck, pero sin orquestador no lo reinicia. Se puede añadir el contenedor willfarrell/autoheal, que reinicia los contenedores no sanos, o una regla de alerta en Prometheus.

Introducción del tema

La documentación vive con el código

Si la documentación está en un documento aparte, se queda desactualizada. En DevOps se escribe en Markdown dentro del repositorio y se revisa en el mismo pull request que el cambio (docs as code). Para un despliegue de contenedores, la documentación mínima es:

  • README: qué es, cómo se ejecuta en local, enlaces al resto.
  • docs/despliegue.md: entornos, requisitos, cómo se despliega (flujo y comandos), cómo se vuelve atrás, variables y secretos (sin valores), verificación.
  • docs/imagen.md: cómo se construye, etiquetas y versionado, variables de entorno, puertos, volúmenes, usuario, healthcheck, ejemplos de docker run.
  • CHANGELOG.md: cambios de cada versión.
  • Metadatos en la propia imagen con las etiquetas estándar OCI, que el registro muestra.
