    Objetivos de la sesión

    1. Gestión de la configuración

    Terraform ha creado las máquinas: tienen sistema operativo, usuario y red. Pero están vacías. Falta instalar Docker, configurar la seguridad, desplegar la aplicación y, después, mantenerlo todo durante meses: parches, cambios de configuración, nuevas versiones. Esa es la tarea de la gestión de la configuración:

    Aprovisionamiento (Terraform)Gestión de la configuración (Ansible)
    Actúa sobreLa plataforma (API de Proxmox, de la nube)El interior de las máquinas (sistema operativo, software)
    CreaVM, redes, discosPaquetes, ficheros de configuración, servicios, usuarios, contenedores
    FrecuenciaCuando cambia la infraestructuraContinuamente: instalación, mantenimiento y despliegues

    Sin gestión de configuración, cada servidor se configura a mano y con el tiempo todos acaban siendo distintos (desviación de configuración). Con ella, el estado de cada servidor está descrito en código, versionado y se puede reaplicar en cualquier momento.

    Herramientas: Ansible (Red Hat, sin agente, push), Puppet y Chef (con agente, pull, más antiguas), Salt (agente o SSH). Usamos Ansible por su sencillez: solo necesita SSH y Python en las máquinas gestionadas.

    2. Arquitectura de Ansible

    • Nodo de control: la máquina donde se instala y se ejecuta Ansible. Solo Linux o macOS (en Windows, con WSL).
    • Nodos gestionados: los servidores que se configuran. Solo necesitan SSH y Python; no se instala ningún agente.
    • Inventario: la lista de nodos, agrupados ([web], [revision]), con variables por nodo o por grupo. Puede ser estático (fichero INI o YAML) o dinámico (un plugin que consulta la API de Proxmox o de la nube).
    • Módulo: un programa que realiza una acción concreta de forma idempotente: apt, copy, template, service, user, docker_container... Ansible lo copia al nodo, lo ejecuta con Python y lo borra.
    • Tarea: una llamada a un módulo con sus parámetros y un nombre.
    • Play: un conjunto de tareas que se aplican a un grupo de nodos.
    • Playbook: un fichero YAML con uno o varios plays.
    • Hechos (facts): datos que Ansible recoge automáticamente de cada nodo al empezar (sistema operativo, IP, memoria...) y que se pueden usar como variables: ansible_distribution_release.
    • become: ejecutar las tareas con privilegios (sudo).
    • Colecciones: paquetes que distribuyen módulos, roles y plugins adicionales (community.docker, community.general, ansible.posix). Se instalan desde Ansible Galaxy.

    Declarativo e idempotente

    Una tarea no dice "instala nginx", sino "nginx debe estar instalado" (state: present). Si ya lo está, el módulo no hace nada y devuelve ok; si no, lo instala y devuelve changed. Por eso un playbook se puede ejecutar cien veces sin riesgo: la segunda vez no debería cambiar nada. Al final de cada ejecución, Ansible muestra un resumen por nodo: ok, changed, failed, unreachable, skipped.

  hosts: web
  become: true
  tasks:
    - name: Paquetes base y SDK de Docker para Python
      ansible.builtin.apt:
        name: [ca-certificates, curl, jq, python3-docker, python3-venv]
        state: present
        update_cache: true
        cache_valid_time: 3600

    - name: Carpeta de claves de repositorios
      ansible.builtin.file:
        path: /etc/apt/keyrings
        state: directory
        mode: "0755"

    - name: Clave del repositorio oficial de Docker
      ansible.builtin.get_url:
        url: https://download.docker.com/linux/ubuntu/gpg
        dest: /etc/apt/keyrings/docker.asc
        mode: "0644"

    - name: Repositorio oficial de Docker
      ansible.builtin.apt_repository:
        repo: "deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu {{ ansible_distribution_release }} stable"
        filename: docker
        state: present

    - name: Docker Engine y plugin Compose
      ansible.builtin.apt:
        name: [docker-ce, docker-ce-cli, containerd.io, docker-buildx-plugin, docker-compose-plugin]
        state: present
        update_cache: true

    - name: Servicio Docker activo al arrancar
      ansible.builtin.service:
        name: docker
        state: started
        enabled: true

    - name: El usuario de despliegue puede usar Docker
      ansible.builtin.user:
        name: despliegue
        groups: docker
        append: true

    1. De playbooks sueltos a roles

    Un playbook con 50 tareas es difícil de leer y de reutilizar. Un rol agrupa todo lo necesario para una responsabilidad concreta (preparar el sistema base, instalar Docker, desplegar la aplicación, monitorizar) con una estructura de carpetas estándar:

    roles/base/
├── defaults/main.yml    # valores por defecto de las variables (prioridad mínima)
├── vars/main.yml        # variables internas del rol (prioridad alta)
├── tasks/main.yml       # tareas
├── handlers/main.yml    # acciones que se ejecutan solo si se notifican
├── templates/           # plantillas Jinja2 (.j2)
├── files/               # ficheros que se copian tal cual
└── meta/main.yml        # dependencias y metadatos del rol

    Se crea con ansible-galaxy role init roles/base y se usa desde un playbook:

    - name: Mantenimiento de los servidores
  hosts: web
  become: true
  roles:
    - base
    - docker

    Los roles se pueden compartir: Ansible Galaxy tiene miles (por ejemplo, geerlingguy.docker). Como cualquier dependencia externa, se revisan y se fijan en requirements.yml.

    2. Variables, plantillas y handlers

    Variables por grupo y por entorno

    ansible/
├── group_vars/
│   ├── all.yml           # para todos los nodos
│   ├── revision.yml      # para el grupo revision
│   └── produccion.yml    # para el grupo produccion

    Ansible tiene más de 20 niveles de precedencia. Los que usaremos, de menor a mayor: defaults del rol → group_vars/all → group_vars/<grupo> → host_vars → vars del play → -e en la línea de órdenes (gana siempre). La idea: el rol trae valores razonables y cada entorno los ajusta. Es el mismo principio que los .tfvars de la unidad 6.

    Handlers

    Un handler es una tarea que solo se ejecuta si otra la notifica y esta ha producido un cambio, y una sola vez al final del play aunque se notifique varias veces. Es la forma idempotente de reiniciar un servicio solo cuando su configuración ha cambiado:

    # tasks
- name: Configuración de SSH endurecida
  ansible.builtin.template:
    src: sshd_extra.conf.j2
    dest: /etc/ssh/sshd_config.d/10-extra.conf
    mode: "0644"
    validate: /usr/sbin/sshd -t -f %s        # no instala una configuración que rompa ssh
  notify: Reiniciar ssh

# handlers
- name: Reiniciar ssh
  ansible.builtin.service:
    name: ssh
    state: restarted

    3. Qué es el mantenimiento

    Mantener un sistema es repetir periódicamente las tareas que lo dejan sano, seguro y homogéneo. Automatizadas, se convierten en un flujo de mantenimiento que se puede ejecutar en todas las máquinas, cuando haga falta y con el mismo resultado:

    5. Ejecutar los flujos de forma periódica

    Un flujo de mantenimiento sirve de poco si hay que acordarse de lanzarlo. Se programa en GitHub Actions en el runner del aula (sesión 34), que tiene acceso a las VM y a la clave de despliegue:

    .github/workflows/mantenimiento.yml

    name: Mantenimiento
on:
  schedule:
    - cron: "0 5 * * 2"          # martes a las 05:00 UTC
  workflow_dispatch:
concurrency:
  group: ansible-revision
  cancel-in-progress: false
jobs:
  mantenimiento:
    runs-on: [self-hosted, linux, aula]
    environment: revision
    defaults:
      run:

    1. ¿Hace lo que debe?

    Un playbook que termina sin errores no garantiza que el sistema haya quedado como queríamos: una tarea puede "cambiar" algo en el sitio equivocado, una plantilla puede generar un fichero válido pero con el valor erróneo, un servicio puede arrancar y caerse a los pocos segundos. El criterio de evaluación pide probar que las acciones automatizadas generan los resultados esperados. Lo hacemos en cuatro niveles, de más barato a más completo:

    NivelPreguntaHerramientaNecesita máquinas

    3. Simulación: modo check y diff

    ansible-playbook mantenimiento.yml --check --diff ejecuta el playbook sin cambiar nada: cada módulo informa de lo que haría, y --diff muestra las diferencias línea a línea en los ficheros. Sirve para:

    • ansible.builtin.service_facts y package_facts: estado de servicios y paquetes.
    • ansible.builtin.uri: peticiones HTTP a la aplicación.
    • ansible.builtin.stat: existencia, permisos y propietario de ficheros.

    2. Seguridad del contenedor

    Un contenedor comparte el kernel con el anfitrión (sesión 5). Si un atacante toma el control de la aplicación, las opciones de ejecución deciden cuánto daño puede hacer. El objetivo es la defensa en profundidad: varias capas, de modo que si una falla, las demás siguen protegiendo.

    • Usuario sin privilegios. Por defecto, los procesos de un contenedor se ejecutan como root (UID 0), y ese root es el mismo UID que el root del anfitrión: si escapa del contenedor, es root en el servidor. Nuestro Dockerfile ya usa USER app; user en el despliegue lo garantiza aunque la imagen no lo haga. (Más allá: el modo rootless de Docker o Podman, y los user namespaces, hacen que incluso el root del contenedor sea un usuario sin privilegios fuera.)
    • Sistema de ficheros de solo lectura: impide que un atacante modifique el código o deje herramientas. Las carpetas que la aplicación necesita escribir (/tmp) se montan como tmpfs en memoria.
    • Capacidades de Linux: el poder de root está dividido en unas 40 capacidades (CAP_NET_ADMIN, CAP_SYS_ADMIN, CAP_CHOWN, CAP_NET_BIND_SERVICE...). Docker concede por defecto unas 14. Una aplicación web no necesita ninguna: capabilities_drop: [ALL]. Si alguna hace falta (por ejemplo, escuchar en el puerto 80 dentro del contenedor), se añade solo esa.
    • no-new-privileges: impide que un proceso gane privilegios con binarios setuid (como sudo).
    • Perfiles del kernel: seccomp filtra las llamadas al sistema permitidas (Docker aplica un perfil por defecto que bloquea unas 40 peligrosas) y AppArmor/SELinux limitan a qué ficheros y recursos accede el proceso. Nunca se deben desactivar ni usar --privileged.
    • Red: redes de Docker propias por aplicación y entorno; publicar solo los puertos necesarios y, si detrás hay un proxy, solo en 127.0.0.1. Recordad (sesión 37) que los puertos publicados por Docker se saltan UFW.
    • Nada de montar el socket de Docker (/var/run/docker.sock) en contenedores de aplicación: equivale a darles root en el anfitrión.
    • Secretos: mejor como ficheros montados de solo lectura o con un gestor de secretos que como variables de entorno, que aparecen en docker inspect.
    • Imagen: mínima (slim, distroless), escaneada (sesión 29) y fijada por versión o digest.

    Estas reglas coinciden con las del CIS Docker Benchmark, que se puede comprobar automáticamente con docker-bench-security.

    3. Niveles de servicio

    • SLI (Service Level Indicator): una métrica que mide el servicio. Por ejemplo, el porcentaje de peticiones a /citas que responden bien en menos de 300 ms.
    • SLO (Service Level Objective): el objetivo interno para ese indicador. Por ejemplo, 99,5 % al mes.
    • SLA (Service Level Agreement): el compromiso contractual con el cliente, normalmente menos exigente que el SLO y con penalizaciones (unidad 2).
    • Presupuesto de errores: lo que queda hasta incumplir el SLO. Con 99,5 % mensual, unas 3,6 horas de fallo al mes. Si se agota, se frenan los cambios arriesgados y se prioriza la estabilidad.

    Mecanismos de despliegue que ayudan a cumplir el nivel de servicio:

    • Política de reinicio: no, on-failure[:N] (reinicia si termina con error, hasta N veces), always, unless-stopped (siempre, salvo que se haya parado a mano). En producción, unless-stopped.
    • Comprobación de salud (healthcheck): Docker ejecuta periódicamente una orden dentro del contenedor y lo marca como healthy o unhealthy. Parámetros: interval, timeout, retries y start_period (margen de arranque). Sin orquestador, Docker no reinicia un contenedor unhealthy; lo trataremos en la sesión 41.
    • Parada ordenada: al parar, Docker envía SIGTERM y espera stop_timeout segundos antes de SIGKILL. Gunicorn termina las peticiones en curso si le damos tiempo.
    • Réplicas detrás de un proxy o balanceador para tolerar la caída de una instancia (lo trabajaréis a fondo con orquestadores en el módulo 5166).

    1. Monitorización y observabilidad

    La monitorización responde a preguntas conocidas de antemano: ¿está el servicio en marcha? ¿Cuánta CPU usa? ¿Supera el umbral? La observabilidad es la capacidad de responder también a preguntas nuevas sobre un sistema a partir de los datos que emite, para entender por qué se comporta como se comporta. Se apoya en tres tipos de datos:

    PilarQué esEjemploHerramientas

    Registros (logs)Eventos con texto y contextoGET /citas 200 12ms, un error con su trazaLoki, Elasticsearch, journald

    2. Qué medir

    Las cuatro señales doradas

    El libro de SRE de Google propone vigilar como mínimo, en todo servicio de cara al usuario:

    1. Latencia: cuánto tarda en responder (distinguiendo respuestas correctas y erróneas). Se usan percentiles: el p95 dice que el 95 % de las peticiones tarda menos que ese valor; la media esconde a los usuarios que esperan mucho.
    2. Tráfico: cuánta demanda recibe (peticiones por segundo).
    3. Errores: porcentaje de peticiones que fallan.
    4. Saturación: cuánto le queda al recurso más limitado (CPU, memoria, conexiones).

    Métodos USE y RED

    • USE (para recursos: CPU, memoria, disco, red): Utilization (uso), Saturation (cola o espera), Errors.
    • RED (para servicios): Rate (peticiones por segundo), Errors, Duration (latencia).

    3. Prometheus y Grafana

    Arquitectura

    • Modelo pull: Prometheus pide (scrape) cada cierto tiempo las métricas a cada objetivo en una URL /metrics con formato de texto.
    • Exportadores: programas que exponen métricas de algo que no las expone por sí mismo. node-exporter (CPU, memoria, disco, red del servidor), cAdvisor (consumo de cada contenedor), blackbox-exporter (sondea URL desde fuera: disponibilidad y tiempo de respuesta, justo nuestros SLI).
    • Series temporales: cada métrica tiene un nombre y etiquetas (container_memory_working_set_bytes{name="cita-previa-revision"}). Tipos: counter (solo crece: peticiones totales), gauge (sube y baja: memoria), histogram (distribución: latencias).
    • PromQL: el lenguaje de consultas. rate() calcula la velocidad de un contador; avg_over_time(), max_over_time() y quantile_over_time() resumen periodos; predict_linear() proyecta tendencias.
    • Reglas de alerta: condiciones PromQL que, si se cumplen durante un tiempo, generan una alerta que Alertmanager agrupa y envía (sesión 41).
    • Grafana: visualización. Se conecta a Prometheus como fuente de datos y dibuja paneles; hay miles de paneles públicos en grafana.com.

    5. Informes de rendimiento y plan de capacidad

    Un capacity plan (plan de capacidad) responde a tres preguntas: ¿cuánto consumimos ahora?, ¿cuánto consumiremos si crece la demanda? y ¿cuándo y cómo hay que ampliar? Permite anticipar el crecimiento en lugar de reaccionar cuando el servicio ya se ha caído. Método:

    1. Línea base: medir el consumo en reposo y con cargas conocidas.
    2. Pruebas de carga: aumentar la carga en escalones (por ejemplo, 10, 50 y 100 usuarios concurrentes) y registrar para cada uno: peticiones por segundo, latencia (media y p95), errores, CPU y memoria del contenedor y del servidor.
    3. Consumo por unidad de carga: por ejemplo, "cada 100 peticiones/s consumen 0,3 núcleos y 40 MB".
    4. Identificar el cuello de botella: el primer recurso que se satura (CPU del contenedor por su límite, memoria, número de trabajadores de Gunicorn...).
    5. Previsión: con el crecimiento esperado (campaña de vacunación: demanda ×10 durante 8 semanas), calcular los recursos necesarios dejando un margen (no superar el 70-80 % de uso).
    6. Acciones: escalar vertical (más CPU o memoria: cambiar group_vars o produccion.tfvars) u horizontal (más réplicas o más VM: num_vms), con fecha y responsable.
    7. Umbrales de alerta que avisen antes de llegar al límite.
    8. Revisión periódica del plan con los datos reales.

    1. Automatizar la reacción a los errores

    Los errores van a ocurrir: un despliegue con una versión defectuosa, alguien intentando entrar por SSH con contraseñas, un trabajo nocturno que falla sin que nadie se entere. La diferencia entre un equipo maduro y uno que no lo es está en qué pasa automáticamente cuando ocurren. Cada reacción automática sigue el esquema evento → detección → acción → aviso:

    Los avisos se envían a donde el equipo los vea: correo, Slack, Teams, Discord o Telegram mediante webhooks (una URL a la que se hace un POST), o servicios como ntfy: se publica un mensaje con un simple curl -d "texto" https://ntfy.sh/CANAL y cualquiera suscrito a ese canal (en la aplicación móvil o en la web) lo recibe.     2. Fallos de trabajo en Ansible: block, rescue y always

    Ansible permite agrupar tareas en un block con una sección rescue que se ejecuta solo si alguna tarea del bloque falla (como un try/catch) y una sección always que se ejecuta siempre. Es la forma de implementar un despliegue con vuelta atrás automática:

    roles/app/tasks/main.yml (despliegue con vuelta atrás)

    - name: Desplegar la nueva versión
      community.docker.docker_container:
        name: "cita-previa-{{ entorno }}"
