Infraestructura como código: primeros ficheros con Terraform

CE 6a

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Explicar qué es la infraestructura como código y el hardware definido por software.
  • Instalar Terraform y crear, modificar y destruir recursos desde ficheros.

Introducción del tema

De los clics al código

Crear servidores a mano no es repetible, no deja rastro y no escala. Con la infraestructura como código la infraestructura se define en ficheros que se versionan en Git, se revisan en pull requests y se aplican de forma automática. Es posible porque el hardware actual está definido por software (SDH, SDDC): la CPU, la memoria, los discos y las redes de una VM o de un contenedor se configuran a través de una API.

Terraform en cuatro ideas

  1. Lenguaje HCL, declarativo: describes el estado final, no los pasos.
  2. Proveedores (providers) que traducen HCL a llamadas a la API de cada plataforma: Proxmox, Docker, AWS, Azure...
  3. Estado (terraform.tfstate): relación entre el código y los recursos reales. Contiene datos sensibles: nunca se sube a Git.
  4. Ciclo init, plan, apply, destroy.

infra/main.tf (primera versión, proveedor Docker)

terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.0"
    }
  }
}

provider "docker" {}

resource "docker_image" "web" {
  name = "nginx:1.27-alpine"
}

resource "docker_container" "web" {
  name  = "web-prueba"
  image = docker_image.web.image_id
  ports {
    internal = 80
    external = 8080
  }
}

  4. (15′) Cambiad el puerto externo a 8081 y ejecutad plan. ¿Terraform modifica o reemplaza? Aplicad. Ejecutad apply otra vez: ¿cambia algo? (idempotencia).

Introducción del tema

Un código, varios entornos

Revisión y producción deben ser iguales en forma y distintos en tamaño y datos. Por eso el código no lleva valores fijos: usa variables, y cada entorno tiene su fichero de parámetros .tfvars. Las salidas (outputs) exponen lo que otros procesos necesitarán, como la IP.

infra/versions.tf y main.tf (Proxmox)

terraform {
  required_version = ">= 1.6"
  required_providers {
    proxmox = {
      source  = "telmate/proxmox"
      version = "3.0.1-rc9"   # fijad la versión que indique el profesor (Registry)
    }
  }
  backend "local" {}         # la ruta del estado se pasa en init
}

provider "proxmox" {
  pm_api_url          = var.pm_api_url
  pm_api_token_id     = var.pm_token_id
  pm_api_token_secret = var.pm_token_secret
  pm_tls_insecure     = true   # certificado autofirmado del laboratorio
}

resource "proxmox_vm_qemu" "web" {
  count       = var.num_vms
  name        = "web-${var.entorno}-${count.index + 1}"
  target_node = var.nodo
  pool        = var.pool
  clone       = var.plantilla
  full_clone  = true
  agent       = 1
  os_type     = "cloud-init"
  memory      = var.memoria
  cpu {
    cores = var.cores
  }
  scsihw = "virtio-scsi-single"
  disks {
    ide {
      ide2 {
        cloudinit { storage = var.almacen }
      }
    }
    scsi {
      scsi0 {
        disk {
          size    = var.disco
          storage = var.almacen
        }
      }
    }
  }
  network {
    id     = 0
    model  = "virtio"
    bridge = "vmbr0"
  }
  ipconfig0 = "ip=dhcp"
  ciuser    = "despliegue"
  sshkeys   = var.clave_publica
  tags      = "${var.entorno};terraform"
}

Introducción del tema

Cuatro tipos de acceso

AccesoPreguntaEn nuestro laboratorio
Roles de acceso del usuario¿Qué personas pueden desplegar en cada entorno?Equipos de GitHub y revisores obligatorios del entorno produccion; usuarios de Proxmox
Roles de acceso del código¿Con qué identidad actúa el pipeline?Un usuario técnico y un token de API por entorno, con un rol a medida y limitado a su pool
Acceso al almacenamiento¿En qué almacenes puede escribir?Permiso Datastore.AllocateSpace solo en el almacén asignado; el estado de Terraform en una ruta protegida
Acceso a las API¿Cómo se autentica y desde dónde?Token con separación de privilegios y caducidad, HTTPS, cortafuegos que solo permite el puerto 8006 desde la red del aula

Rol mínimo para Terraform en Proxmox (desde la shell del nodo)

pveum role add TerraformProv -privs "Datastore.AllocateSpace Datastore.Audit Pool.Audit   Sys.Audit VM.Allocate VM.Audit VM.Clone VM.Config.CDROM VM.Config.Cloudinit VM.Config.CPU   VM.Config.Disk VM.Config.HWType VM.Config.Memory VM.Config.Network VM.Config.Options   VM.PowerMgmt SDN.Use"
pveum user add tf-revision@pve --comment "Terraform entorno revisión"
pveum aclmod /pool/revision -user tf-revision@pve -role TerraformProv
pveum aclmod /storage/local-lvm -user tf-revision@pve -role TerraformProv
pveum aclmod /vms/9000 -user tf-revision@pve -role PVEVMUser      # leer la plantilla
pveum user token add tf-revision@pve terraform --privsep 0 --expire $(date -d "+90 days" +%s)

El token solo tiene poder sobre el pool de su entorno. Si se filtra el de revisión, producción no corre peligro. Consultad en la documentación del proveedor la lista exacta de privilegios que necesita vuestra versión.

Dónde guardar cada credencial

  • Nunca en .tf, .tfvars subidos a Git ni en el README.
  • En local: variable de entorno TF_VAR_pm_token_secret (o un gestor de contraseñas).
  • En el pipeline: secretos del entorno de GitHub, distintos en revision y produccion.
  • El estado puede contener datos sensibles: fuera del repositorio y con permisos restringidos.

Actividad

  2. (30′) Configuradlo en la plataforma:
    • Proxmox: con el profesor (o en vuestra VM de prácticas), crear rol, usuarios, permisos por pool y tokens de cada entorno como en el ejemplo.
    • Laboratorio Docker: el acceso a la API de Docker equivale a ser root. Documentad quién pertenece al grupo docker, cread un usuario despliegue sin sudo que solo pueda usar Docker y limitad los volúmenes a una carpeta /srv/revision o /srv/produccion.
  3. (15′) Guardad los secretos en los entornos de GitHub (PM_TOKEN_SECRET en cada uno) y comprobad con terraform plan en local, usando la variable de entorno, que el token de revisión no puede crear máquinas en el pool de producción.

Inicio10′Introducción20′Actividad75′Cierre15′

Introducción del tema

Del plan a la realidad

Hoy aplicamos la definición en la plataforma real con las credenciales del entorno de revisión. Pasos seguros:

  1. Cargar la credencial sin escribirla en el historial de la terminal: read -s TF_VAR_pm_token_secret; export TF_VAR_pm_token_secret.
  2. Inicializar con el estado del entorno: terraform init -backend-config="path=$HOME/tfstate/revision.tfstate".
  3. Guardar el plan y revisarlo antes de aplicar: terraform plan -var-file=revision.tfvars -out=revision.tfplan.
  4. Aplicar exactamente ese plan: terraform apply revision.tfplan.
  5. Consultar las salidas: terraform output -json.

Las salidas (IP de las VM, nombres, URL) son el punto de unión con el resto del proceso: el flujo de trabajo y la unidad 7 (Ansible) las leerán para saber dónde actuar.

Flujo de trabajo para desplegar la infraestructura

CE 6b

Inicio10′Introducción20′Actividad75′Cierre15′

Qué vas a saber hacer al terminar

  • Crear un flujo que valide y planifique en cada pull request y despliegue por entornos al fusionar.
  • Usar las credenciales de cada entorno y la aprobación obligatoria de producción.

Introducción del tema

Por qué un runner autohospedado

Los runners de GitHub están en Internet y no ven el Proxmox del aula (ni el Docker de vuestro portátil). Instalamos un runner autohospedado en una máquina de la red del aula: ejecuta los trabajos de GitHub Actions localmente. Como es persistente, podemos guardar el estado de Terraform en una ruta fija de esa máquina (en un entorno profesional se usaría un backend remoto con bloqueo, como S3 o el de GitLab).

.github/workflows/infraestructura.yml

name: Infraestructura
on:
  pull_request:
    paths: ["infra/**"]
  push:
    branches: [main]
    paths: ["infra/**"]
  workflow_dispatch:

defaults:
  run:
    working-directory: infra

jobs:
  validar-y-planificar:
    runs-on: [self-hosted, linux]
    environment: revision
    env:
      TF_VAR_pm_token_secret: ${{ secrets.PM_TOKEN_SECRET }}
    steps:
      - uses: actions/checkout@v4
      - run: terraform fmt -check -recursive
      - run: terraform init -input=false -backend-config="path=$HOME/tfstate/revision.tfstate"
      - run: terraform validate
      - run: terraform plan -input=false -var-file=revision.tfvars

  desplegar-revision:
    if: github.ref == 'refs/heads/main'
    needs: validar-y-planificar
    runs-on: [self-hosted, linux]
    environment: revision
    env:
      TF_VAR_pm_token_secret: ${{ secrets.PM_TOKEN_SECRET }}
    steps:
      - uses: actions/checkout@v4
      - run: terraform init -input=false -backend-config="path=$HOME/tfstate/revision.tfstate"
      - run: terraform apply -input=false -auto-approve -var-file=revision.tfvars
      - run: ./verificar.sh revision

  desplegar-produccion:
    needs: desplegar-revision
    runs-on: [self-hosted, linux]
    environment: produccion          # espera la aprobación del equipo operaciones
    env:
      TF_VAR_pm_token_secret: ${{ secrets.PM_TOKEN_SECRET }}
    steps:
      - uses: actions/checkout@v4
      - run: terraform init -input=false -reconfigure -backend-config="path=$HOME/tfstate/produccion.tfstate"
      - run: terraform apply -input=false -auto-approve -var-file=produccion.tfvars
      - run: ./verificar.sh produccion

Cada trabajo toma el secreto de su entorno: el mismo nombre, PM_TOKEN_SECRET, tiene un valor distinto en revisión y en producción. Si usáis el laboratorio Docker, los trabajos son iguales sin la variable del token.

Actividad

  1. (20′) Instalad el runner en el portátil de la pareja (o en la VM que indique el profesor): Settings, Actions, Runners, New self-hosted runner, Linux x64, y seguid los comandos. Arrancadlo con ./run.sh y comprobad que aparece como Idle. Instalad Terraform en esa máquina si no lo está.
  2. (25′) Añadid el workflow y un verificar.sh provisional que solo haga terraform output (lo completaremos en la sesión 35). Abrid un PR con un cambio en infra/ y comprobad que se ejecuta el plan y aparece en el registro del trabajo.
  3. (15′) Fusionad: comprobad que se despliega revisión y que producción queda esperando aprobación. Aprobad desde la cuenta de operaciones.
  4. (15′) Probad los fallos: un error de sintaxis en el PR (¿se para en fmt o en validate?), y un secreto de producción incorrecto (¿qué error da y en qué paso?). Documentadlo en el README.
Puesta en común

Recorremos el flujo completo en el proyector, del PR a producción, y comentamos qué pasaría si dos personas fusionan a la vez.

Evidencia de evaluación

Notas para el docente

Introducción del tema

Desplegado no es lo mismo que funcionando

Que terraform apply termine bien solo significa que la API aceptó las peticiones. Hay que verificar que cada recurso existe, es accesible y tiene la configuración pedida:

  • Sin desviación: terraform plan -detailed-exitcode devuelve 0 si no hay cambios pendientes y 2 si los hay.
  • Cómputo: la VM responde (ping) y acepta SSH con la clave de despliegue.
  • Recursos: CPU, memoria y disco dentro de la VM coinciden con los parámetros (nproc, free -m, lsblk).
  • Red: resolución de nombres y salida a Internet (necesaria para instalar paquetes en la unidad 7).
  • Seguridad: solo están abiertos los puertos esperados.

infra/verificar.sh

#!/usr/bin/env bash
set -euo pipefail
ENTORNO=${1:?Uso: verificar.sh revision|produccion}
fallos=0
ok()  { echo "OK    $*"; }
mal() { echo "FALLO $*"; fallos=$((fallos+1)); }

terraform plan -input=false -detailed-exitcode -var-file="$ENTORNO.tfvars" >/dev/null   && ok "sin desviaciones respecto al código" || mal "hay cambios pendientes o error en plan"

for ip in $(terraform output -json ips | jq -r '.[]'); do
  ping -c1 -W2 "$ip" >/dev/null && ok "$ip responde a ping" || mal "$ip no responde"
  if ssh -o BatchMode=yes -o ConnectTimeout=5 -o StrictHostKeyChecking=accept-new despliegue@"$ip"        'nproc; free -m | awk "/Mem/{print \$2}"; getent hosts github.com >/dev/null' > /tmp/v.txt; then
    ok "$ip SSH, cores=$(sed -n 1p /tmp/v.txt), memoria=$(sed -n 2p /tmp/v.txt) MB, DNS correcto"
  else
    mal "$ip sin acceso SSH o sin DNS"
  fi
done
echo "Verificación de $ENTORNO terminada con $fallos fallos"
exit $fallos

Actividad

  1. (30′) Completad verificar.sh para vuestra plataforma (en el laboratorio Docker: docker inspect del contenedor, curl a cada URL de las salidas y comprobación de la red). Añadid al menos una comprobación de seguridad (por ejemplo, nc -z a un puerto que debe estar cerrado).
  2. (15′) Hacedlo ejecutable, probadlo en local y subidlo. Comprobad que el workflow lo ejecuta tras cada despliegue y que un fallo detiene el paso a producción.
  3. (10′) Provocad una desviación (apagad una VM o parad un contenedor a mano) y comprobad que la verificación lo detecta.
  4. (20′) Entrega: README de infra/ con arquitectura, ficheros, flujo y registro de una verificación completa de revisión y producción. Revisad la rúbrica de la pestaña Presentación.

No destruyáis la infraestructura de revisión: la usamos en la unidad 7.
