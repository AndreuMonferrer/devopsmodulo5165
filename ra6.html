    1. De los clics al código

    En las unidades 2 a 4 creamos máquinas, redes y buckets con la consola: pulsando botones. Funciona para aprender, pero en un entorno real tiene problemas graves:

    • No es repetible: montar el entorno de producción igual que el de revisión depende de que alguien recuerde y repita cada clic.
    • No deja rastro: no se sabe quién cambió qué ni por qué.
    • No escala: crear 50 máquinas a mano es lento y propenso a errores.
    • No se puede revisar antes de aplicarlo.
    • Recuperarse de un desastre exige reconstruirlo todo de memoria.

    La infraestructura como código (IaC) consiste en definir la infraestructura en ficheros de texto que se guardan en un repositorio Git, se revisan en pull requests, se prueban y se aplican automáticamente con una herramienta. Se trata a la infraestructura como al software: con control de versiones, revisión, pruebas y CI/CD.

    Beneficios

    • Reproducibilidad: el mismo código crea entornos idénticos (revisión y producción iguales en forma).
    • Trazabilidad: el historial de Git dice quién cambió qué, cuándo y por qué.
    • Revisión: los cambios de infraestructura pasan por pull request y se ve el plan antes de aplicarlos.
    • Velocidad: crear o destruir un entorno completo lleva minutos.
    • Documentación viva: el código describe exactamente lo que hay.
    • Recuperación ante desastres: reconstruir desde el código.

    Hardware definido por software (SDH)

    La IaC es posible porque el hardware actual está definido por software: la CPU, la memoria, los discos y las tarjetas de red de una máquina virtual no son piezas físicas que haya que instalar, sino parámetros que se configuran a través de una API. Lo mismo ocurre con las redes (SDN, redes definidas por software) y el almacenamiento (SDS). Cuando todo el CPD se gestiona así se habla de centro de datos definido por software (SDDC). El criterio de evaluación lo menciona expresamente: los ficheros de Terraform que escribiremos para Proxmox (sesión 31) son la definición del hardware de nuestras máquinas en el lenguaje de la plataforma.

    Enfoques de IaC

    • Declarativo (Terraform, CloudFormation, Bicep): se describe el estado final deseado y la herramienta calcula las acciones.
    • Imperativo (scripts con la CLI, SDK): se escriben los pasos. Hay que controlar a mano si algo ya existe.
    • Con lenguajes de programación (Pulumi, AWS CDK): declarativo por debajo, pero escrito en Python, TypeScript o Go.

    Y según qué gestionan: aprovisionamiento de recursos (Terraform: crea la VM) frente a gestión de la configuración (Ansible: instala y configura el software dentro de la VM, unidad 7).

    2. Terraform y OpenTofu

    Terraform (HashiCorp, 2014) es la herramienta de IaC multiplataforma más extendida. En 2023 cambió su licencia a BSL (no libre), y la comunidad creó el fork OpenTofu, libre y mantenido por la Linux Foundation. Son compatibles en lo que veremos: podéis usar terraform o tofu indistintamente.

    Arquitectura

    • Núcleo: lee los ficheros, construye un grafo de dependencias entre recursos, compara el estado deseado con el conocido y calcula qué crear, cambiar o destruir.
    • Proveedores: plugins que traducen los recursos a llamadas a la API de cada plataforma. Hay miles en el Registry (registry.terraform.io; OpenTofu tiene el suyo compatible). Cada uno documenta sus recursos y argumentos.
    • Estado (terraform.tfstate): fichero JSON que relaciona cada recurso del código con el objeto real (su identificador) y guarda sus atributos. Terraform lo necesita para saber qué gestiona. Puede contener datos sensibles (IP, contraseñas generadas): nunca se sube a Git. En equipos se guarda en un backend remoto con bloqueo (S3, Azure Storage, GitLab, Terraform Cloud) para que dos personas no lo modifiquen a la vez.

    3. El lenguaje HCL

    HCL (HashiCorp Configuration Language) se organiza en bloques con un tipo, etiquetas y un cuerpo con argumentos:

    tipo_de_bloque "etiqueta1" "etiqueta2" {
  argumento = valor
  bloque_anidado {
    otro = "valor"
  }
}
    BloquePara quéEjemplo
    terraformVersión de Terraform, proveedores requeridos, backendrequired_providers { docker = {...} }
    providerConfiguración del proveedor (URL de la API, credenciales)provider "docker" {}
    resourceUn objeto que Terraform crea y gestionaresource "docker_container" "web" {...}
    dataConsulta información que ya existe, sin gestionarladata "docker_network" "bridge" {...}
    variableParámetro de entradavariable "puerto" { type = number }
    outputValor de salida para personas o para otros procesosoutput "url" { value = ... }
    localsValores calculados reutilizableslocals { nombre = "cp-${var.entorno}" }
    moduleReutilizar un conjunto de ficherosmodule "red" { source = "./modulos/red" }

    Referencias, expresiones y dependencias

    • Un recurso se referencia como TIPO.NOMBRE.ATRIBUTO: docker_image.app.image_id. Las variables como var.nombre, los locales como local.nombre.
    • Interpolación en cadenas: "cita-previa-${var.entorno}".
    • Tipos: string, number, bool, list(...), map(...), object({...}).
    • Funciones: upper(), join(), length(), lookup()...; condicional cond ? a : b.
    • count y for_each crean varias instancias de un recurso.
    • Dependencias implícitas: si un recurso usa un atributo de otro, Terraform sabe que debe crearlo después. Las explícitas se declaran con depends_on (raramente necesario).

    4. El ciclo de trabajo

    OrdenQué hace
    terraform initDescarga los proveedores, prepara el backend. Crea .terraform/ y el fichero de bloqueo de versiones .terraform.lock.hcl (este sí se sube a Git).
    terraform fmtDa formato estándar a los ficheros.
    terraform validateComprueba la sintaxis y la coherencia sin conectarse a la plataforma.
    terraform planConsulta el estado real y muestra qué haría: + crear, ~ modificar, - destruir, -/+ reemplazar. No cambia nada.
    terraform applyCalcula el plan, pide confirmación y lo ejecuta. Con terraform plan -out=x.tfplan + terraform apply x.tfplan se aplica exactamente el plan revisado.
    terraform outputMuestra las salidas.
    terraform state list / showConsulta lo que hay en el estado.
    terraform destroyDestruye todo lo gestionado por esa configuración.

    Idempotencia y desviación

    Si se aplica dos veces la misma configuración, la segunda vez no ocurre nada: el estado real ya coincide con el deseado (idempotencia). Si alguien cambia o borra algo a mano, el siguiente plan detecta la diferencia (desviación, drift) y propone corregirla. Por eso, en un entorno gestionado con IaC, no se toca nada a mano: cualquier cambio se hace en el código.

    Modificar o reemplazar

    Algunos cambios se pueden aplicar sobre el objeto existente (modificación en el sitio); otros obligan a destruirlo y crearlo de nuevo (reemplazo), porque la plataforma no permite cambiar ese atributo. El plan lo indica con # forces replacement. Es importante leerlo: reemplazar una base de datos significa perder sus datos.

  default     = 1

    condition     = var.num_vms >= 1 && var.num_vms <= 4

  type = string
  validation {
    condition     = contains(["revision", "produccion"], var.entorno)

}

variable "pm_token_secret" {
  type      = string
  sensitive = true          # no se muestra en plan, apply ni output

    • default: si no tiene, la variable es obligatoria.
    • sensitive: oculta el valor en la salida. Ojo: sí se guarda en el estado.

    2. El modelo de permisos de Proxmox

    • Usuarios en un dominio de autenticación (realm): @pam (usuarios del sistema Linux del nodo), @pve (usuarios propios de Proxmox), o LDAP/Active Directory/OpenID.
    • Grupos de usuarios.
    • Privilegios: permisos atómicos, como VM.Allocate (crear VM), VM.Clone, VM.Config.Memory, VM.PowerMgmt (encender y apagar), Datastore.AllocateSpace (crear discos en un almacén), Sys.Audit...
    • Roles: conjuntos de privilegios. Hay predefinidos (Administrator, PVEAdmin, PVEVMAdmin, PVEVMUser, PVEAuditor, PVEDatastoreUser...) y se pueden crear a medida.
    • Rutas (objetos): / (todo), /nodes/pve, /vms/101, /storage/local-lvm, /pool/revision, /sdn/....
    • ACL: una entrada "usuario o grupo + rol + ruta", que se hereda hacia abajo si está marcada como propagable.
    • Pools: agrupaciones de VM y almacenes. Dar permisos sobre un pool es la forma de delimitar un entorno.
    • Tokens de API: credenciales para programas, asociadas a un usuario, con caducidad opcional y revocables. Con separación de privilegios (--privsep 1), el token solo tiene los permisos que se le asignen explícitamente, que nunca pueden superar los del usuario; sin ella, hereda todos los del usuario.

    1. Del plan a la realidad: el procedimiento seguro

    1. Cargar la credencial sin que quede escrita en el historial ni en disco: 
      read -s TF_VAR_pm_token_secret; export TF_VAR_pm_token_secret

    3. Validar: terraform fmt -check y terraform validate.
    4. Planificar y guardar el plan: 
      terraform plan -var-file=revision.tfvars -out=revision.tfplan
    5. Revisar el plan: número de recursos a crear, modificar y destruir. Si aparece algún destroy o forces replacement inesperado, parar.

    2. Qué ocurre durante apply

    1. Terraform recorre el grafo de dependencias y lanza las operaciones en paralelo cuando no dependen unas de otras (por defecto, hasta 10 a la vez; -parallelism=N lo cambia). Con Proxmox conviene bajar el paralelismo si el nodo va justo: -parallelism=2.
    2. El proveedor llama a la API de Proxmox: clonar la plantilla (una tarea que se ve en el registro de tareas de la web), configurar CPU, memoria, disco, red y cloud-init, y arrancar la VM.
    3. Dentro de la VM, en el primer arranque, cloud-init crea el usuario despliegue, instala la clave SSH, redimensiona el disco al tamaño pedido y configura la red por DHCP.
    4. El agente de QEMU (qemu-guest-agent, instalado en la plantilla) informa a Proxmox de la IP obtenida, y el proveedor la guarda en el estado.
    5. Terraform guarda en el estado cada recurso creado a medida que se crea.

    5. Proteger los recursos: lifecycle

    resource "proxmox_vm_qemu" "bd" {
  # ...
  lifecycle {
    prevent_destroy       = true          # plan falla si algo implica destruirlo
    create_before_destroy = false         # en reemplazos: crear el nuevo antes de borrar el viejo
    ignore_changes        = [tags]        # no corregir cambios en estos atributos hechos fuera de Terraform
  }
}

    Flujo de trabajo para desplegar la infraestructura

    CE 6b

    Objetivos de la sesión

    • Diseñar un flujo de trabajo de CI/CD para infraestructura: validar y planificar en cada pull request, aplicar por entornos al fusionar.
    • Elegir entre runners de GitHub y runners autoalojados, y conocer los riesgos de seguridad de estos últimos.
    • Usar las credenciales de cada entorno desde el flujo y exigir la aprobación de producción.
    • Evitar ejecuciones simultáneas sobre el mismo estado y detectar desviaciones de forma programada.
    • Poner en marcha el flujo infraestructura.yml para Cita Previa.

    1. Por qué un flujo de trabajo para la infraestructura

    En la sesión 33 aplicamos Terraform desde el portátil. Funciona, pero depende de quién lo ejecuta, con qué versión, con qué credenciales y si revisó el plan. Llevarlo a un flujo de trabajo automatizado aporta lo mismo que la CI/CD al código de la aplicación:

    • Todo cambio de infraestructura pasa por pull request, con su plan visible para quien revisa.
    • Se aplica siempre igual, desde un entorno controlado, con las credenciales del entorno y nunca con las de una persona.
    • Producción solo se modifica con aprobación y después de haber aplicado y verificado revisión.
    • Queda registro de quién aprobó qué y cuándo.

    Diseño del flujo

    2. Dónde se ejecuta: runners

    Runner de GitHubRunner autoalojado (self-hosted)
    Dónde estáMáquina efímera en la nube de GitHubUna máquina vuestra (portátil, VM del aula)
    Ve la red del aula (Proxmox)NoSí

    Nuestro Proxmox no es accesible desde Internet, así que necesitamos un runner autoalojado dentro de la red del aula. El runner es un programa que se conecta a GitHub (conexión saliente, no hay que abrir puertos), espera trabajos etiquetados para él y los ejecuta en esa máquina.

    Riesgo de seguridad. En un repositorio público, cualquiera puede abrir un pull request desde un fork; si el workflow se ejecuta en vuestro runner, ejecutaría código ajeno dentro de la red del aula. Medidas: en Settings → Actions → General, exigir aprobación para ejecutar workflows de colaboradores externos; no usar el runner autoalojado en trabajos que se disparen desde forks; ejecutarlo con un usuario sin privilegios; y, si es posible, hacer el repositorio privado mientras dura la unidad. En entornos profesionales se usan runners efímeros (una máquina nueva por trabajo).

    3. Credenciales, estado y concurrencia

    • Credenciales: cada trabajo declara environment: revision o environment: produccion y recibe secrets.PM_TOKEN_SECRET de ese entorno. El mismo nombre de secreto tiene valores distintos según el entorno (sesión 32). Se pasa a Terraform como variable de entorno TF_VAR_pm_token_secret.
    • Estado: al ser el runner persistente, el estado vive en $HOME/tfstate/ de esa máquina, con permisos 600. En un entorno profesional se usaría un backend remoto con bloqueo (S3 con bloqueo, GitLab, Terraform Cloud) y cifrado.
    • Concurrencia: si dos personas fusionan a la vez, dos apply podrían ejecutarse sobre el mismo estado. concurrency los pone en cola: 
      concurrency:
  group: infraestructura
  cancel-in-progress: false      # nunca cancelar un apply a medias
    • Versiones: fijad la versión de Terraform en el runner (required_version) y la del proveedor (.terraform.lock.hcl en Git) para que el flujo sea reproducible.

    if: github.ref == 'refs/heads/main'

    Verificar la infraestructura desplegada

    CE 6e

    Objetivos de la sesión

    • Explicar por qué "desplegado" no significa "funcionando" y qué niveles de verificación existen.
    • Comprobar tras cada despliegue que se obtiene acceso a todos los recursos creados: cómputo, red, almacenamiento, credenciales y API.
    • Conocer herramientas de verificación de infraestructura: scripts, bloques check de Terraform, Testinfra, Goss, InSpec.

    1. Desplegado no es lo mismo que funcionando

    Que terraform apply termine con Apply complete! solo significa que la API de la plataforma aceptó las peticiones. Puede ocurrir que:

    • la VM se haya creado pero no arranque, o arranque sin red;
    • cloud-init haya fallado y no exista el usuario de despliegue o la clave SSH;
    • la VM no resuelva nombres o no salga a Internet (y Ansible no pueda instalar nada en la unidad 7);
    • el disco no tenga el tamaño pedido porque no se ha redimensionado;
    • haya puertos abiertos que no deberían;
    • el agente no informe de la IP y las salidas estén vacías.

    Por eso, después de cada despliegue se verifica la infraestructura: se comprueba que cada recurso existe, es accesible con las credenciales previstas y tiene la configuración pedida. Si la verificación falla, el despliegue se considera fallido y no se continúa hacia producción.

    2. Qué verificar

    NivelPreguntaCómo comprobarlo
    Coherencia con el código¿Lo real coincide con lo declarado?terraform plan -detailed-exitcode devuelve 0 (sin cambios)
    Existencia en la plataforma¿Existen los recursos, en el pool y con las etiquetas correctas?API de Proxmox (/cluster/resources) con el token del entorno

    Una buena verificación es automática (se ejecuta sin intervención), repetible (se puede lanzar en cualquier momento), rápida, con un resultado claro (código de salida 0 si todo va bien, distinto de 0 si no) y que deja registro.

    3. Herramientas

    • Scripts de Bash: sencillos y sin dependencias. Los usaremos.
    • Bloques check de Terraform (≥ 1.5): aserciones que Terraform evalúa en cada plan y apply; si fallan, avisan (sin detener la aplicación). Útiles para comprobaciones de salud tras crear recursos:

    • Testinfra (Python/pytest), Goss (YAML) e InSpec (Ruby): marcos para describir el estado esperado de un servidor ("el paquete X está instalado", "el puerto 22 escucha", "el usuario existe") y comprobarlo.
    • Terratest (Go): pruebas de infraestructura que crean, verifican y destruyen entornos completos.

    4. El script de verificación

    infra/verificar.sh

    #!/usr/bin/env bash
# Verifica la infraestructura de un entorno tras el despliegue.
# Uso: ./verificar.sh revision|produccion
set -uo pipefail
ENTORNO=${1:?Uso: verificar.sh revision|produccion}
VARS="$ENTORNO.tfvars"
fallos=0
ok()  { echo "OK    $*"; }
mal() { echo "FALLO $*"; fallos=$((fallos+1)); }
valor() { sed -n "s/^$1 *= *\"\{0,1\}\([^\"]*\)\"\{0,1\}.*/\1/p" "$VARS"; }

echo "== Verificación de $ENTORNO ($(date -Iseconds))"

# 1. Coherencia con el código
terraform plan -input=false -detailed-exitcode -var-file="$VARS" >/dev/null
case $? in
  0) ok "sin desviaciones respecto al código" ;;
  2) mal "hay cambios pendientes: la realidad no coincide con el código" ;;
  *) mal "error al ejecutar plan" ;;
esac

# 2. Recursos esperados según los parámetros
CORES=$(valor cores); MEMORIA=$(valor memoria); NUM=$(valor num_vms)
mapfile -t IPS < <(terraform output -json ips | jq -r '.[]')
[ "${#IPS[@]}" -eq "$NUM" ] && ok "${#IPS[@]} máquinas (esperadas $NUM)" || mal "${#IPS[@]} máquinas, esperadas $NUM"

for ip in "${IPS[@]}"; do
  [ -n "$ip" ] || { mal "máquina sin IP"; continue; }
  ping -c1 -W2 "$ip" >/dev/null && ok "$ip responde a ping" || mal "$ip no responde a ping"

  # 3. Acceso con la credencial de despliegue y datos del sistema
  if datos=$(ssh -o BatchMode=yes -o ConnectTimeout=5 -o StrictHostKeyChecking=accept-new despliegue@"$ip" \
      'nproc; free -m | awk "/Mem/{print \$2}"; cloud-init status | cut -d" " -f2;
       getent hosts github.com >/dev/null && echo dns-ok;
       curl -sI --max-time 5 https://ghcr.io >/dev/null && echo salida-ok;
       sudo sshd -T | grep -i "^passwordauthentication"'); then
    ok "$ip acceso SSH con la clave de despliegue"
    mapfile -t d <<< "$datos"
    [ "${d[0]}" = "$CORES" ] && ok "$ip núcleos=${d[0]}" || mal "$ip núcleos=${d[0]}, esperados $CORES"
    # la memoria visible es algo menor que la asignada
    [ "${d[1]}" -ge $((MEMORIA * 85 / 100)) ] && ok "$ip memoria=${d[1]} MB" || mal "$ip memoria=${d[1]} MB, esperados ~$MEMORIA"
    [ "${d[2]}" = "done" ] && ok "$ip cloud-init terminado" || mal "$ip cloud-init: ${d[2]}"
    grep -q dns-ok    <<< "$datos" && ok "$ip resuelve nombres" || mal "$ip no resuelve nombres"
    grep -q salida-ok <<< "$datos" && ok "$ip sale a Internet" || mal "$ip no sale a Internet"
    grep -qi "passwordauthentication no" <<< "$datos" && ok "$ip SSH sin contraseña" || mal "$ip admite contraseña por SSH"
  else
    mal "$ip sin acceso SSH con la clave de despliegue"
  fi

  # 4. Seguridad: puertos que deben estar cerrados
  # (en la unidad 7, al desplegar la aplicación, el 80 pasará a ser un puerto esperado)
  for p in 80 3306 5432; do
    nc -z -w2 "$ip" "$p" 2>/dev/null && mal "$ip puerto $p abierto (no debería)" || ok "$ip puerto $p cerrado"
  done
done

echo "== $ENTORNO: $fallos fallos"
exit $(( fallos > 0 ))
